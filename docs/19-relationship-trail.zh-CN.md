## 变更概要（v1 → v3）

v1 只写了"联系人清单"。沟通中需求持续扩展，v3 是重写不是追加：

| 类型 | 内容 |
|---|---|
| **add** | **公司架构框架**：组织 → 部门/团队 → 人的层级线，即"架构图" |
| **add** | **跨公司关系线**：A 司的 b1 和 C 司的 b2 有关系（老同事 / 认识 / 推荐） |
| **add** | **影响因素标签**：任何一条记录被打上标签后，从"记录"变成某个决策的**影响因素**；因素是多元的，本期归四类：组织变动 / 同事关系 / 外部机会 / 自我需求 |
| **add** | **决策原因视图（本期重点）**：一个决策由哪些因素推着、哪些拉着，每条都能点回出处；系统摆因素、不下结论 |
| **add** | **图谱交互**：节点-连线图，分类筛选、拖拽、缩放、点击看详情（形态参考人生图谱） |
| **modify** | v1 §2.3 "不做关系图谱连线"这条**撤销**。撤销的前提写在 §4.5：**每条线都必须有来源，系统不推断任何一条关系** |
| **add** | **组织变动预警（用户说的"离职提醒"）**：记下"A 司 c 组并入 b 组"后，系统提醒"你图上有 3 个人在 c 组"。**只做事实提醒，不预测任何人会不会离职**，原因见 §5.7 |
| **modify** | 数据模型从"一张联系人表"改为"节点 + 边"；联系人成为节点的一种 |
| **keep** | v1 的全部边界不变：不打分、不推断、归属唯一、不编职责、可删干净 |

## 0. 一句话

> 我联系过哪家公司、找的谁、他管什么、他跟别家的谁认识；A 司架构调整了、同事关系变了、
> 外面来了个机会、我自己也有想要的东西——**这些事互相牵扯，我脑子里理不清。**
> 让阿桥把它画成一张图：架构是架构，关系是关系，
> **哪些因素在推我、哪些在拉我，一条条摆出来，带出处——但决定还是我自己做。**
> 而且当图上有东西动了（某个组被合并了），**主动告诉我一声，别等我自己发现。**

## 1. 需求来源与问题定义

### 1.1 用户原话（按沟通顺序）

1. "关系脉络记录的，比如哪家公司我找了什么人，但是职责我记不住，它自动帮我梳理，这样我就可以一目了然了，而不是自己去整理。"
2. "公司架构框架+关系脉络，比如 A 司的 b1 和 C 司的 b2 是有关系的。就是会有架构图+关系线。"
3. "还有就是重点决策原因。"
4. "比如 A 司架构调整，同事关系，外部机会，自我需求。"
5. "而且影响的因素是多元的。"
6. "得有个标签，变成影响因素。"
7. "还有就是最好会有个离职提醒。"
8. "比如 A 司的 c 业务组并入 b 组。"
9. "那这一群人都会流入市场。"
10. "c 组老大可能就会看机会。"

### 1.2 这是个什么问题（大白话）

一个人在做职业选择的时候，脑子里同时装着四种完全不同的东西：

| 装着什么 | 例子 | 特点 |
|---|---|---|
| **组织在变** | A 司架构调整，原来的部门被合并 | 外部发生的、有时间点的事件 |
| **人在变** | 一起共事过的老同事去了 C 司 | 关系，跨公司、跨时间 |
| **机会在来** | 外部来了个岗位 | 有时效、有条件 |
| **自己在变** | 想要更稳定 / 想学新东西 / 要照顾家里 | 主观的、会变的 |

**这四类东西的共同点是：它们各自都记得住，但是它们"怎么互相牵扯"记不住。**
人脑存得下"张姐在 A 司做招聘"，也存得下"A 司要合并部门"，
但存不下"A 司合并部门 → 张姐那条线可能作废 → 所以外部这个机会的紧迫性变了"。

**丢的不是信息，是信息之间的连线。** 而连线恰恰是做决定的时候唯一有用的那部分。

现在用户只能自己在脑子里连，或者自己画表格——**这就是"自己去整理"，也就是本需求要去掉的那件事。**

### 1.3 严重程度与影响面

| 维度 | 判断 |
|---|---|
| 影响人群 | 所有正在做职业选择的用户；联系人 ≥3 或候选路径 ≥2 时必然发生 |
| 后果 | 找错人、错过时效、做完决定说不出为什么、过几个月复盘时当初的理由已经丢了 |
| 严重程度 | **高**（v1 评估为中高，因为 v1 只解决"记不住职责"这一层，v2 解决的是"理不清因果"这一层） |
| 现状替代 | 自己记备忘录 / 自己画图 / 靠感觉 |

## 2. 目标与非目标

### 2.1 目标

1. **架构看得见**：用户接触过的公司，能看到"部门—人"的层级线（只画用户真知道的那部分）。
2. **关系连得起**：跨公司的人和人之间，能连线并写明关系类型和来源。
3. **因素标得出**：任何一条记录（一个人、一次架构调整、一个机会、一个自我需求）都能被打上标签，成为某个决策的**影响因素**，带**推力/阻力**。
4. **原因摆得清**（本期重点）：打开一个决策，一眼看到"推我的几条 / 拉我的几条"，每条点得回出处；系统不给结论。
5. **变化留得住**：架构调整、关系变化都是**事件**，追加不覆盖；三个月后还能回答"我当初为什么这么想"。
6. **动了有人告诉我**：图上某个组织单元发生变化时，主动提醒"你图上有几个人在那里"——
   **只说发生了什么、谁在那里，不预测任何人会不会离职**（§5.7）。

### 2.2 成功判据（可验收）

- 用户问"我在 A 司都认识谁、都什么岗？"→ 一次给出层级结构，未知的地方明说未知。
- 用户问"这个机会我到底该不该去？"→ 给出**推力 / 阻力 / 不确定**三栏 + 用户自己定的门槛逐条三态，**并且明确说这个决定由用户自己做**（校验器阻断任何形式的结论）。
- 图上任意一条线，点开都能看到"这条线是哪来的"（哪一轮对话、哪份材料）。
- 系统从未画出过一条用户没说过的关系线（阻断级校验 + 围栏测试）。

### 2.3 非目标（本期明确不做）

| 不做 | 为什么 |
|---|---|
| 系统**推断**关系（"你们可能认识"） | 无来源的连线就是编造。见 §4.5 |
| 给人打分 / 给机会排序 / 算"匹配度" | 与 `no_candidate_scoring`、`no_eligibility_verdict` 同源。系统摆因素，用户做判断 |
| 替用户做决定 / 给"建议选 B" | 这是本产品的 founding sentence 的正面冲突。见 §6.3 |
| 自动上网抓第三方公开资料 | 替一个没跟本服务打过交道的人建档。见 §4.4 |
| 预测某个人会不会离职 / 出"离职可能性"排行 | 对一个没同意过任何事的第三方做意图预测，并据此接触他。**这是本期最重要的一条边界，完整推理见 §5.7** |
| 完整企业组织架构库 | 我们只知道用户告诉我们的那几个点。假装完整就是编造。见 §5.3 |
| 多人协作/共享图谱 | 图上全是第三方信息，共享要单独设计。见 §10 待拍板 5 |

## 3. 名词字典（代码 / 文档 / 界面必须一致）

| 中文 | 英文（代码） | 含义 |
|---|---|---|
| 脉络图谱 | trail graph | 本功能整体 |
| 节点 | `Node` | 图上一个点：组织 / 单元 / 人 / 事件 / 机会 / 需求 / 决策 |
| 边 | `Edge` | 图上一条线，分三类，见下 |
| 架构线 | structure edge | 人 → 部门 → 公司 的隶属/汇报线，构成"架构图" |
| 关系线 | relation edge | 人和人之间：老同事 / 认识 / 引荐 |
| 影响线 | influence edge | 影响因素 → 决策，带**极性**和**用户自评的分量** |
| 影响因素 | factor | 被打上标签、挂到某个决策上的节点 |
| 推力 / 阻力 | push / drag | 影响线的极性。不用"正/负"——阻力不等于坏事 |
| 决策 | `Decision` | 用户正在做的一个选择 |
| 决策门槛 | gate | 用户**自己定**的、这个决策必须回答的问题 |
| 满足 / 不满足 / 不确定 | met / unmet / unknown | 门槛的三态，口径与 `criteria_explain` **完全一致** |
| 组织变动预警 | alert | 图上某个组织单元发生变化时的一条提醒。**是事实提醒，不是意图预测** |
| 传闻 / 已证实 | hearsay / confirmed | 事件的证实状态。默认是**传闻** |
| 待确认 | unconfirmed | 某字段没有可追溯来源时的状态（**是一个状态，不是空值**） |

## 4. 边界：这个功能凭什么能在这个产品里成立

**这一节是全文最重要的部分。** 本产品的底线是"不认定资格，不给人打分"，
`talent_sourcing` 一整章拒绝了"替雇主给人建库"。而 v2 要做的是：给人建库、画关系网、还要参与决策。
**下面五条是它能成立的全部理由。任何一条被削弱，这个功能就该被砍掉，而不是打个折扣继续做。**

### 4.1 归属唯一：这张图只属于画它的那个用户

| 约束 | 强制点 |
|---|---|
| 不跨用户可见 | store 层按 `subject_id` 过滤，过滤写在 store 内部而不是调用方（与 `DiscoverableProfiles` 同一手法：调用方忘了检查会 fail open，store 里忘不了） |
| 不进入任何检索池 | 不参与 `opportunity_search` / `candidate_search` / 任何 retrieval |
| 不参与聚合 | `supply_demand_insight` 够不到（围栏测试） |
| recruiter 完全够不到 | 工具不在 `talent_sourcing` allowlist（围栏测试） |
| 能删干净 | 单节点 / 整家公司 / 整张图；沿用 `ForgetProfile` 的先例 |

### 4.2 只记"事务位置"，不做"人物画像"

只记：哪家单位、什么职务、管哪一段、和谁什么关系、聊到哪、下一步找谁。
**不记**：性格、态度、好不好说话、靠不靠谱。这类主观判断**不设结构化字段**，
用户自己说了就存进 `Note`（原话），**不参与任何分组、排序、筛选、图上的视觉编码**。

> **为什么**：只要有了"评价"字段，它就会被排序；排序就是打分；打分就是本产品拒绝的那件事，
> 只不过对象从求职者换成了 HR。这条一破，`no_candidate_scoring` 那一整章的推理就白写了。

### 4.3 绝不编造职责，也绝不编造关系

用户要这个功能的前提就是**他自己记不住**——这意味着**系统编的东西他没能力判断真假**。
他会当真，然后照着去打电话、去准备材料、去做决定。

> 一条编造的职责，比一个空着的职责危害大得多。
> 空着他知道要去问；编了，他不会去问。
> **一条编造的关系线更糟：它会直接改变他找谁。**

对应两道**阻断级**校验器（与既有 `no_invented_identifiers` 同形）：

- `no_invented_role`：回答里的每个职务/职责，必须在 `Provenance` 里找得到来源。
- `no_invented_edge`：回答里断言的每条关系，必须对应图上一条**有来源**的边。

### 4.4 来源受限：只收用户给的，不去替用户打听

职责和关系的来源只有两种被允许：**用户自己说的**、**用户提供的材料**（名片、通知、邮件签名）。
**系统上网查第三方**本期不做——那是本服务主动去搜集一个从没跟本服务打过交道、
也没同意过任何事的人的信息。`talent_sourcing` 的推理是"没有人默认在池子里"，这里同理。

> 例外：**机会**（外部岗位）可以走既有的 `opportunity_search` / 全国检索。
> 机会是公开发布的信息，人不是。这条界线要一直守住。

### 4.5 图上没有一条线是系统连的（v1 撤销那条非目标的前提）

v1 曾把"关系图谱连线"列为不做，理由是"推断出来的关系没有来源"。v2 把它做起来，
**前提是把"推断"和"记录"彻底分开**：

| 允许 | 禁止 |
|---|---|
| 用户说"b1 和 b2 是老同事" → 画一条线，标注来源 | 系统看到两人都在 A 司待过 → 自己连一条线 |
| 用户说"张姐介绍我认识了李工" → 画一条引荐线 | 系统根据姓氏/部门/时间"猜"关系 |
| 图上一条线可以显示为**虚线 = 待确认**（用户说得不确定） | 图上不存在"系统认为可能有关系"这种线 |

**为什么这个区分能成立**：因为画出来的东西用户会当成事实。
一条实线在图上和一条推断线长得一模一样，而用户没有办法区分——所以干脆让推断线不存在。

## 5. 方案设计

### 5.1 三层结构（对应需求里的三件事）

```
第三层  决策层   ┌─ 决策：要不要去 C 司 ────────────────┐
              │   门槛（用户自己定的问题）→ 三态判定    │   ← "重点决策原因"
              │   推力 3 条 / 阻力 2 条 / 不确定 1 条   │
              └──────────▲──────────────────────────┘
                         │ 影响线（带极性，用户打标签才有）  ← "得有个标签，变成影响因素"
第二层  因素层   ┌────────┴─────────┬──────────┬──────────┐
              │ 组织变动         │ 同事关系  │ 外部机会  │ 自我需求 │   ← "影响的因素是多元的"
              │ (A司架构调整)     │ (b1↔b2)  │ (C司岗位) │ (要稳定) │
              └────────▲─────────┴─────▲────┴──────────┘
                       │               │
第一层  事实层   组织 ─ 部门 ─ 人 ────── 关系线 ────── 人 ─ 部门 ─ 组织   ← "架构图+关系线"
              A 司                                        C 司
```

**为什么分三层而不是一张平图**：
人生图谱那张参考图之所以能看懂，是因为**每一类节点回答的是不同的问题**
（北极星回答"要去哪"、资产回答"我有什么"、风险回答"会踩什么"）。
如果把"人"和"决策"混在一层，图会变成一团只有作者本人看得懂的毛线。
分层之后，**一层只回答一个问题**：事实层回答"有谁"，因素层回答"什么在影响我"，决策层回答"我为什么这么想"。

### 5.2 领域模型

```go
// NodeKind 是图上一个点的种类。种类是封闭枚举而不是自由字符串:
// 每加一种都要同时想清楚它的边怎么连、在图上什么颜色、会不会被打分。
type NodeKind string

const (
    NodeOrg         NodeKind = "org"          // 公司 / 机构
    NodeUnit        NodeKind = "unit"         // 部门 / 团队 / 科室  —— 架构图的中间层
    NodePerson      NodeKind = "person"       // 人（v1 的"联系人"）
    NodeEvent       NodeKind = "event"        // 发生的事，如"A 司架构调整"。有时间点，追加不覆盖
    NodeOpportunity NodeKind = "opportunity"  // 外部机会。引用既有 domain.Opportunity，不复制
    NodeNeed        NodeKind = "need"         // 自我需求
    NodeDecision    NodeKind = "decision"     // 我正在做的一个选择
)

type Node struct {
    ID        string
    SubjectID string     // 归属：画它的用户。所有读写以它为过滤条件
    Kind      NodeKind
    Label     string     // 图上显示的名字
    Org       string     // person/unit 所属组织（分组键）
    RoleTitle string     // person: 职务
    Duty      string     // person: 实际管什么
    OccurredAt *time.Time// event: 什么时候发生的
    Ref        string    // opportunity: 指向 domain.Opportunity.ID；need: 指向 Profile 字段
    Note       string    // 用户原话。不参与任何排序/分组/视觉编码
    Unconfirmed []string  // 哪些字段还没有来源。序列化必须是 [] 不是 null
    Provenance  map[string]string // 字段 → 来源（对话轮次 id / 材料 ref），与 Profile 同形
    CreatedAt, UpdatedAt time.Time
}

type EdgeKind string

const (
    // 架构线：构成"架构图"
    EdgeBelongsTo EdgeKind = "belongs_to"  // person → unit → org
    EdgeReportsTo EdgeKind = "reports_to"  // person → person（汇报线）
    // 关系线：跨公司的人和人
    EdgeColleague EdgeKind = "colleague_of" // 共事过（可带"在哪家、什么时候"）
    EdgeKnows     EdgeKind = "knows"
    EdgeReferred  EdgeKind = "referred_by"  // 引荐
    // 影响线：因素 → 决策。只有用户打了标签才存在
    EdgeInfluences EdgeKind = "influences"
)

type Edge struct {
    ID        string
    SubjectID string
    Kind      EdgeKind
    From, To  string   // Node.ID
    Context   string   // colleague_of: "2019-2021 在 A 司同一个项目"
    // 仅 influences 有:
    Polarity  string   // "push"(推力) | "drag"(阻力)
    Weight    int      // 1-3，用户自评的分量。系统永不写这个字段。见 §6.4
    Confirmed bool     // false → 图上画虚线。见 §4.5
    Provenance string  // 这条线是哪来的。为空 = 这条边不该存在
    CreatedAt time.Time
}
```

**三个刻意的设计决定，和它们的原因：**

| 决定 | 为什么 |
|---|---|
| `Provenance` 为空的边视为非法数据，store 层直接拒收 | 让"每条线都有来源"成为**类型/存储层的性质**，而不是靠调用方自觉。校验器是第二道，不是第一道 |
| `Weight` 只能由用户写，系统永不写 | 系统一旦能写分量，就等于系统在给因素排序，也就是在替用户做决定。见 §6.4 |
| 机会节点用 `Ref` 引用既有 `domain.Opportunity`，不复制字段 | **单一真相源**。机会的标题、截止日期、条件已经在语料/检索里有权威副本，复制一份就会过期，而用户会照着过期的那份去准备材料 |

### 5.3 架构图必须画成"残缺的"

用户对一家公司的了解，永远只有他接触过的那几个点：认识张姐、知道她上面有个总监、
不知道旁边还有几个部门。

**所以架构图默认就是残缺的，界面必须把残缺画出来**：

- 已知节点：实线框。
- 用户提过但没细节的：虚线框 + "未知"。
- **没有的地方就是空的，不补，不画一棵看起来完整的树。**

> **为什么这条重要到要单独列一节**：一棵漂亮完整的组织树会让用户以为"系统知道这家公司的架构"。
> 他会照着这棵树去判断该找谁——而这棵树里凡是他没说过的部分，都只能是编的。
> **界面上"看起来完整"本身就是一种编造，即使每个字段都是空的。**

### 5.4 标签 → 影响因素（用户明确要的机制）

任何一个节点（人 / 事件 / 机会 / 需求）都可以被**打标签**，挂到某个决策上。打标签这个动作产生一条影响线：

```
[A司架构调整]  --影响-->  [要不要去C司]     极性: 推力   分量: 2   来源: 8/29 对话
[张姐这条线]   --影响-->  [要不要去C司]     极性: 阻力   分量: 1   来源: 8/21 对话
[要照顾小孩]   --影响-->  [要不要去C司]     极性: 阻力   分量: 3   来源: profile.constraints
```

**四类因素（用户给的四个例子，正好是四个来源域）**，图上四种颜色，也是筛选 chips：

| 类别 | 来自哪 | 例子 |
|---|---|---|
| 组织变动 | `event` 节点 | A 司架构调整、部门合并、领导换人 |
| 同事关系 | `person` 节点 + 关系线 | 老同事去了 C 司、张姐那条线断了 |
| 外部机会 | `opportunity` 节点 | C 司的岗位、某个培训名额 |
| 自我需求 | `need` 节点（引用 profile） | 要稳定、要学新东西、要照顾家里 |

**两个关键设计决定：**

1. **标签是用户打的，系统只能"建议"，不能自己挂。**
   系统可以在回答末尾说一句"要不要把这条挂到『要不要去 C 司』上？"，
   但**挂不挂、是推力还是阻力、多重，全是用户说了算**。
   > **为什么**：极性和分量就是价值判断。系统自己挂 = 系统在替用户排列价值观。
   > 这跟 `no_cohort_downranking` 拦的是同一件事：系统不替人决定什么对他更重要。

2. **一个因素可以同时是推力和阻力（挂两条线到不同决策）。**
   "A 司架构调整"对"要不要去 C 司"是推力，对"要不要留下争取新岗位"可能也是推力。
   > **为什么**：现实里因素本来就是多义的，强行让它只有一个极性，用户就得在两个决策之间反复改标签，
   > 最后他会放弃用这个功能。

### 5.5 决策原因视图（**本期重点**）

打开一个决策节点，看到的是这个（不是一段 AI 总结）：

```
决策：要不要去 C 司                                   开始于 8/29 · 还没定

我的门槛（我自己定的 3 条）
  ① 有没有明确负责的模块？          不确定  ← 还没跟 b2 确认
  ② 通勤能不能 17:30 前到家？        不满足  ← 单程 70 分钟（8/30 你说的）
  ③ 有没有社保衔接？                满足    ← C 司 HR 8/29 明确说有

推着我走的（3）                          拉着我留的（2）
  A 司架构调整，我那条线要合并 [8/29]      要照顾小孩，17:30 必须到家 [档案]
  b2 在 C 司，能带我熟悉 [8/29]           A 司的张姐还在帮我争取新岗位 [8/21]
  C 司岗位薪资高 15% [C 司 JD]

还不知道的（1）
  C 司这个团队会不会也重组 —— 下次可以问 b2：「这个团队今年有过调整吗？」

──────────────────────────────────────────────
这些是你告诉我的因素，我把它们摆在一起了。
门槛是你自己定的，判断也是你自己做的 —— 这个决定不由我来下。
```

**四个设计决定和原因：**

| 决定 | 为什么 |
|---|---|
| **门槛由用户自己定**，系统只负责逐条读成三态 | 这与既有 `criteria_explain` 是**同一个机制**：读出条件、标三态、从不下结论。用的是同一条推理和同一套校验器口径，不是新发明。参考图里的"决策门槛五问"就是这个东西的手工版 |
| **推力/阻力两栏并列，不合并成一个分数** | 一个分数是"一个别人不能反驳的结论"；两栏是"一组你可以逐条反驳的理由"。这正是 `no_candidate_scoring` 那一章里"可见的理由 vs 一个数字"的同一条推理 |
| **"还不知道的"单独成栏，而且给一句能直接问出口的话** | 只标"不确定"是把问题扔回给用户，而用户的困难恰恰是不知道怎么问。给一句能直接念的问话，才是把"记不住/不知道"变成"下次能问清楚" |
| **结尾那句"这个决定不由我来下"是固定的，不是文案** | 由 `no_decision_verdict` 校验器保证。一个把因素摆得这么清楚的界面，天然会让用户觉得"系统已经算出答案了"——必须显式打断这个错觉 |

### 5.6 变化是事件，追加不覆盖

"A 司架构调整"不是把张姐的部门字段改掉，而是**新增一个 event 节点**，并把旧的隶属边标记为"截止于 8/29"。

> **为什么**：
> ① 三个月后用户复盘"我当初为什么这么决定"，需要看到的是**当时**的架构和**当时**的因素，
> 覆盖式更新会让历史决策的理由凭空消失；
> ② 架构调整本身就是最重要的一类影响因素——把它写成一次字段更新，这个因素就没了。

### 5.7 组织变动预警（用户说的"离职提醒"）· **本节是本期最重要的边界判断**

**需求原话**："最好会有个离职提醒。比如 A 司的 c 业务组并入 b 组，那这一群人都会流入市场，c 组老大可能就会看机会。"

#### 先把这句话拆成三步，因为第三步踩线了

| 步 | 内容 | 性质 | 能不能做 |
|---|---|---|---|
| ① | A 司 c 组并入 b 组 | **事实记录**（用户听来的一件事） | ✅ 能 |
| ② | 这群人会流入市场 | **群体层面的市场判断**，不指向具体某个人 | ⚠️ 有条件，见下 |
| ③ | c 组老大可能会看机会 | **对一个具体的、真实存在的、没同意过任何事的人，预测他的就业意图** | ❌ 不能 |

第 ③ 步为什么是这个产品明确拒绝的：

- **它是对第三方的预测性画像**，而且预测的是这个人本人从来没表达过的意图。
- **它会被拿去主动联系他，而这可能真的伤到他**：公司还没正式宣布，一个外部人先来问
  "听说你们组要没了"，会把他置于很难的位置——包括在他自己公司里的位置。
- **它建立在传闻上**。用户听来的组织调整经常不准，而基于错误传闻的接触，
  **代价是由被联系的那个人承担的，不是由系统、也不是由用户承担**。
- `18-recruiter-and-outreach.md` 一整章的推理是"没有人默认在池子里、名字不会自己走出去"。
  ③ 是这条推理的正面反面。

#### 所以本期这样做：把 ① 做足，③ 的结论留给用户自己下

对比两种写法。**差别看起来只是措辞，实质是"谁下的结论"**：

| ❌ 系统下结论 | ✅ 系统摆事实 |
|---|---|
| "c 组老大王五**可能会看机会**，建议现在联系他" | "A 司 c 组并入 b 组（8/29 · 你听说的，未证实）。你图上在 c 组的有 3 个人：王五（组长）、张三、李四。" |
| 系统替一个不在场的人宣布了他的处境和意图 | 系统只说了两件用户自己告诉过它的事：发生了什么、谁在那里 |
| 用户没法反驳——他不知道系统凭什么这么说 | 每一条都能点回出处，也就都能被反驳 |
| 一旦有多条，必然要排序 → "最可能离职榜" | 没有可排序的东西 |

**这不是文字游戏。** 右边那条同样让用户在第一时间知道该关注谁，
但它不制造任何关于第三方意图的断言，也不制造一个"离职可能性"的排序。
用户完全可以自己得出"王五可能会看机会"这个判断——
**这本来就该是他的判断，因为承担误判后果的是他和王五，不是系统。**

形状上，这与既有的 `criteria_explain` 完全一致：**摆出事实、标明不确定、把结论留给有权下结论的人。**
本产品到目前为止每一次遇到"要不要替用户下结论"，给的都是这同一个答案。

#### 触发机制：一次图查询，零模型推理

```
用户记下事件：A 司 · c 业务组 并入 b 业务组 · 8/29 · 来源: 听说(未证实)
        ↓   store 层的一次连通查询（不经过模型）
图上匹配：unit = "c 业务组" 的 person 节点 → 王五(组长)、张三、李四
        ↓
生成一条预警，进「我的概览」，不打断当前对话
```

预警卡片：

```
⚠ 组织变动 · A 司                                     8/29 · 未证实
  c 业务组 并入 b 业务组

  你图上在 c 组的有 3 个人：王五（组长）、张三、李四

  这条你标的是「听说」，还没证实。        [标为已证实]  [标为不实]
  要把这件事挂成某个决策的影响因素吗？     [挂到…]

  下次可以问王五：「你们组这次调整，你那块是怎么安排的？」
```

四个设计决定和原因：

| 决定 | 为什么 |
|---|---|
| **触发是图查询，不是模型判断** | 结果可复现、可解释、可测试。让模型来判断"谁会离职"，同一份数据两次会给不同答案，而且**没法写围栏**——不可测试的判断在这个产品里等于没有约束 |
| **必须带 传闻 / 已证实 状态，默认"传闻"** | 用户听来的调整经常不准。默认未证实，是让用户**每一次都看见这个不确定性**，而不是只在第一次看见 |
| **预警里不出现任何"可能性""紧急度"分数** | 一有分数就会被排序；排序就是给人排"最可能离职榜"——正是 `no_person_scoring` 拦的那件事 |
| **一个事件只提醒一次，不反复推** | 反复提醒等于催促行动。这个功能的定位是"别错过"，不是"快去联系" |

#### 被提醒的那个人的处境（这一节不能省）

王五从没跟这个服务打过交道，也没同意过任何事。他出现在这张图上的唯一原因，是用户跟他打过交道。所以：

- 图上关于他的信息，**只有用户自己知道的那些**，系统不去替用户打听（§4.4）；
- 系统对他的意图、处境、稳定性**不下任何判断**；
- 预警**不触发任何自动联系**。真要联系：resident 自己去联系；
  recruiter 角色则仍必须走 `outreach_request` 的人工审批 + 本人接受的握手链路，**一步不少**。

#### 关于第 ② 步（"这群人会流入市场"）

群体层面、不指向具体个人的判断，本产品其实**已经有一个专门的地方**放它：
`supply_demand_insight`——它带着 k-匿名下限、覆盖率标注、"只讲相关不讲因果"三条约束。

如果要做"某地区某类岗位近期供给可能增加"这种判断，**应该走那条意图的那套约束**，
而不是在个人的图谱里长出一个简化版。**本期不做**，见 §10 待拍板 8。

#### 如果一定要做"离职可能性"排序——那是另一个产品

它需要：第三方数据源、对个人的评分模型、以及一套完全不同的合规论证
（当事人如何知情、如何反对、错误如何纠正）。
它与本产品"不认定资格、不给人打分"的底线是**正面冲突**，不是加个开关能解决的。
**建议单独立项评估，不要从这个功能里长出来。** 见 §10 待拍板 1。

### 5.8 界面

**位置**：「我的概览」新增「脉络图谱」入口 → 全屏图谱视图（对话区仍是主区，图谱是打开的一个面板）。

**图谱视图**（形态参考人生图谱，交互一致）：

- 顶部分类 chips：全部 / 组织 / 人 / 组织变动 / 同事关系 / 外部机会 / 自我需求 / 决策（带数量）。
- 交互：拖拽节点、滚轮缩放、点击看详情、重置。
- 视觉编码**只编码事实**：颜色 = 节点类别，线型 = 实线（已确认）/ 虚线（待确认），
  **大小不编码重要性**（大小=重要性就是打分）。
- 点击节点 → 右侧详情面板：字段 + 每个字段的来源 + 待确认项 + 相关的接触记录时间线。
- 点击决策节点 → 直接进 §5.5 的决策原因视图。

**降级**：图谱是**增强**，不是主路径。渲染失败 / 低带宽（`low_bandwidth` 访问需求）时，
自动退回文字版分组清单，功能不缺失。
> **为什么**：本产品的用户里有一部分是低带宽、大字号、窗口协助场景。
> 一个只能靠力导向图才能用的功能，对他们等于不存在。

### 5.9 工具（最小集合）

| 工具 | 风险 | 做什么 |
|---|---|---|
| `graph_node_upsert` | 低 | 新建/更新节点。无来源字段必须同时写入 `Unconfirmed`，schema 强制 |
| `graph_edge_upsert` | 低 | 新建/更新边。**`Provenance` 为空直接拒绝** |
| `graph_query` | 只读 | 查图：按公司、按类别、某个决策的全部因素、待确认清单 |
| `decision_upsert` | 低 | 建决策、写门槛（门槛文本只能来自用户） |
| `graph_forget` | 不可逆 | 删节点 / 整家公司 / 整张图 |

参数 schema 一律 `additionalProperties: false`（沿用既有约定）——
模型无法把"匹配度""推荐指数""靠谱程度"这类字段偷渡进来，调用在进入 `Run` 之前就被拒。

### 5.10 校验器

| 校验器 | 严重级 | 拦什么 |
|---|---|---|
| `no_invented_role` | **阻断** | 职务/职责没有来源就说出口 |
| `no_invented_edge` | **阻断** | 断言一条图上不存在或无来源的关系 |
| `no_decision_verdict` | **阻断** | "建议你去 C 司""综合来看 C 司更好""匹配度 85%"——任何形式的结论或分数 |
| `unconfirmed_is_stated` | 修复 | 把待确认信息说成确定的；修复方向固定：**什么确定、什么不确定、由谁来定** |
| `no_person_scoring` | 阻断 | "最该找的人是 X""b2 比张姐有用"——`no_candidate_scoring` 的泛化 |
| `no_third_party_intent` | **阻断** | 断言第三方的意图或处境："他可能会离职""他现在不稳定""这群人会流入市场"。见 §5.7 |

复用既有：`no_false_reassurance`、`reply_language`、`actionable_next_step`、`citations_present`。

> **注意 `no_decision_verdict` 与 `no_eligibility_verdict` 的关系**：形状相同，对象不同
> （前者管"人生选择"，后者管"资格结论"）。是否合并见 §10 待拍板 6。

## 6. 挂在哪里：意图还是能力

需求说的是"加一个 intent"。这里要先对齐口径，因为它决定实现形状。

**本仓库的 `intent` 不是"功能"，是"受众"**——`internal/intent/intent.go` 的注释写得很明白：
新受众是新增一行。现有五个意图分别是 个人 / 高摩擦人群 / 服务机构 / 用人单位 / 政策规划，
全部是"谁在说话"。

而"脉络图谱"不是新受众：**是同一个 resident，在办同一件事的过程中要用的一个能力。**

### 方案 A：新增第六个意图 `relationship_trail`

- **好处**：边界写进登记表、被 `TestVerifiersExist` 守住；界面有独立意图卡片。
- **代价**：
  ① 破坏"intent = 受众"的一致性，登记表语义从此变成"受众 + 有时候是功能"；
  ② **路由歧义**："我联系过的那家公司下一步该干嘛"该路由到哪个意图？分错就拿不到工具；
  ③ **致命**：自动记录必须发生在**任意**对话里，而意图一次只有一个——做成独立意图，
  用户必须先切过去才记得上，**"自动帮我梳理"就废了**。

### 方案 B（推荐）：新增一组能力，挂进现有意图

- **做法**：5 个工具 + 图存储 + 5 个校验器 + 「我的概览」一个入口，
  加入 `individual_pathway`、`low_access_support`、`service_orchestration` 的 allowlist。
- **好处**：① 用户在原对话里顺口一说就记上了，**这正是"自动"的落点**；
  ② 无路由歧义；③ 登记表语义保持干净。
- **代价**：校验器要挂三处（被 `TestVerifiersExist` 守住，成本可控）；没有独立意图卡片，
  功能的存在感靠「我的概览」入口承载。

> **推荐 B。理由不是省事，而是 A 在产品目标上就是坏的**：
> 需求的关键词是"自动"和"不用我自己整理"，而独立意图天然要求用户先声明"我现在要整理关系"——
> 那就又变回用户自己组织了。

以下 §7 之后按方案 B 展开；若拍 A，数据模型、校验器、界面全部可直接复用，只多一行登记表。

## 9. 指标

| 指标 | 为什么看它 |
|---|---|
| 待确认职责/关系的补齐率 | 对应"职责我记不住"是否真被解决 |
| 决策原因视图的打开次数 / 决策数 | 对应本期重点是否被用上 |
| 用户手动纠正条数 / 自动记录条数 | 纠正率高 = 抽取质量差，最早的质量信号 |
| 预警 → 用户实际做了动作（标证实 / 挂成因素 / 去联系）的比例 | 预警是不是真的"没让人错过"，还是变成了噪音 |
| `no_decision_verdict` / `no_invented_edge` / `no_third_party_intent` 触发次数 | **不追求为零**。归零通常意味着它没在跑，而不是模型不编了 |

## 10. 待拍板（按优先级）

### 1. 这张图到底服务谁：个人，还是招聘方 / 猎头？（最高优先级，阻塞 §4.1 和 §5.7）

需求里的例子——"这一群人都会流入市场""c 组老大可能就会看机会"——**是猎头 / BD 的语言**，
而 v1/v2 的全部边界（尤其 §4.1：recruiter 完全够不到这张图）是按**个人用户**写的。
**这两者不能同时成立，必须先定。**

| 选项 | 形态 | 代价 |
|---|---|---|
| **A. 只服务个人（resident）** ← 推荐先做 | 图是"我的关系和我的决策"；预警的意义是"我认识的人处境变了，我要不要关心 / 要不要借这个机会" | 满足不了猎头场景 |
| **B. 也给 recruiter 用，但只在既有握手链路内** | recruiter 能画自己的图、能收组织变动预警；**但接触仍必须走 `outreach_request` 人工审批 + 本人接受**，图上依然没有评分和意图预测 | 要拆掉 §4.1"recruiter 够不到图"这条围栏并重新论证；`18-recruiter-and-outreach.md` 要同步改 |
| **C. 做成猎头线索产品** | 离职可能性排序、第三方数据源、主动触达 | **与本产品底线正面冲突**，应单独立项，不建议从这里长出来（§5.7 末） |

> **这条不定，§4.1、§5.7、角色 allowlist、围栏测试全都定不了。**
> 我的判断：先按 **A** 做完 P1–P7，B 作为下一版的一次显式扩权（连同它要改的那一章文档）。

### 2. 做成第六个意图，还是跨意图的能力？（阻塞其余设计）

见 §6。**推荐 B（能力）**。核心理由：独立意图要求用户先切过去才记得上，与"自动"直接冲突。
若坚持 A，需接受路由歧义 + 登记表语义破坏。

### 3. 本期做到 P6（决策原因）+ P7（预警），还是一直做到 P8（图谱可视化）？

- 做到 **P7**：需求的核心（记录 / 梳理 / 决策原因 / 别错过）已全部满足，界面是文字版分组 + 两栏 + 预警卡片。
- 做到 **P8**：拿到参考图那种可拖拽的图谱。**但图谱是展示层，它不产生任何新信息。**
- **推荐先 P7，P8 下一版**。另一个理由：图谱一旦先做，会强烈诱导把"重要性"编码成节点大小或位置——**那就是打分**。

### 4. 是否新增授权范围 `store_graph`？

- **不新增**：复用 `store_profile`。省一个开关，但"记住我自己"和"记住我认识的人和他们的关系"是两种暴露面。
- **新增**（推荐）：已有先例——`ConsentDiscoverable` 就是因为"被统计"和"被雇主搜到"是两回事才单列。代价：授权面板多一项。

### 5. 允不允许系统上网补全第三方信息（职务、公司架构、组织调整新闻）？

**推荐不允许**（§4.4）。注意这条和预警是连着的：如果允许系统去抓"某司组织调整"的公开新闻，
预警就能自动触发而不必等用户听说——**但那同时意味着系统开始主动跟踪一批第三方**。
这是隐私决策，不是功能开关，若要开必须单独设计（查什么、存不存、如何标来源、第三方如何反对）。

### 6. `caseworker` 能不能用？

窗口人员记"我找了哪个科室的谁"价值很高，但那是**工作关系**，归属应是机构而非个人，
离职后这份图归谁？**推荐本期只开 `resident`**，caseworker 单独立项。

### 7. `no_decision_verdict` 独立，还是并进 `no_eligibility_verdict`？

形状相同、对象不同。合并省一个校验器，但会把既有那个的语义从"资格结论"扩大到"人生建议"，
它现有的围栏测试可能不再覆盖新语义。**推荐独立**，理由是两者将来的修复文案会分叉。

### 8. `Weight`（用户自评分量）要不要做？

- **做**：用户能表达"这条对我特别重要"，决策原因视图能按分量排序。
- **不做**（保守）：完全不引入任何数字，只有推力 / 阻力两栏。
- **风险**：一旦有了数字，下一步必然有人提"能不能算个总分"——**而总分就是结论**。
- **推荐做，但锁死**：用户自评、永不聚合、永不求和、界面上不出现任何总分，并配围栏测试。

### 9. 群体层面的市场信号（"这群人会流入市场"）做不做？

**推荐本期不做**。它属于 `supply_demand_insight` 的领域，那条意图已经带着
k-匿名下限、覆盖率标注、只讲相关不讲因果三条约束。
在个人图谱里长一个简化版，等于把那三条约束绕过去。见 §5.7。
