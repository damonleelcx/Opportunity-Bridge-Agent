## 0. 为什么它是独立产品，而不是阿桥的一个功能

阿桥的底线是**不认定资格、不给人打分**。本产品的核心恰恰是给组织和岗位打分排序、
判断"什么时候该联系谁"。**这两件事不能装在同一个意图登记表里**——
装进去就等于把阿桥那套边界推翻，而那套边界是它对用户的承诺。

**复用什么、不复用什么：**

| 复用 | 不复用 |
|---|---|
| 图存储、幂等写入、迁移规范 | 阿桥的意图登记表（`internal/intent`） |
| Agent 循环（understand→plan→act→verify→respond） | 阿桥的五个意图和它们的边界 |
| 校验器框架（`internal/guardrail`） | `no_candidate_scoring` 等禁止打分的校验器 |
| 人工审批机制（`RiskIrreversible` + 参数哈希） | 面向居民的授权范围模型 |

## 1. 一句话与核心洞察

> **组织在变的时候，人才会动。**
> 别人拿到的是一份静态的人才库；本产品拿到的是**你自己的关系网 + 组织正在发生的变化 + 你离目标还有几步**。

### 1.1 核心洞察（产品能成立的那句话）

主流工具（领英、Apollo、各类简历库）卖的是**人的静态档案**——联系方式、履历、技能。
这类数据是**同质的**：谁都买得到，谁都在发同样的开发信，回复率被打到地板。

真正决定成单的是两件档案里没有的东西：

| 变量 | 为什么它决定成败 |
|---|---|
| **时机** | 同一个人，组织重组后的三个月和平常的三个月，接电话的概率完全不同 |
| **路径** | 陌生开发信 vs "张三让我联系你"，是两个数量级的回复率 |

**所以本产品的两个核心资产是：组织变动事件流（时机）+ 你自己的关系图（路径）。**
这两样都不是买来的，是攒出来的——也就构成了别人拿不走的壁垒。

### 1.2 触发这个产品的那个场景

> "A 司的 c 业务组并入 b 组，那这一群人都会流入市场，c 组老大可能就会看机会。"

拆开看，它就是本产品的完整工作流：

```
组织变动情报  →  谁在那里（图查询） →  时机判断（可解释评分） →  怎么够到他（路径） →  触达与跟进
   §6              §5                    §7                      §8              §4.5
```

## 4. Agent 怎么工作（本节回答"用什么意图、什么工具"）

**前提：整理和更新是 Agent 的活，不是用户的活。**
用户只负责说话、确认、纠错；**建节点、连边、发现冲突、发现过期、发现该问什么，全部由 Agent 做。**
一个需要用户自己填表维护的图，三周之后一定是废的——这是这类产品最常见的死法。

### 4.1 意图的划分维度必须换一个（重要设计决定）

阿桥的登记表里 **intent = 受众**（居民 / 窗口 / 雇主 / 政策）。
本产品**只有一类受众**（猎头 / 招聘方），受众维度切不出东西来。

**所以这里的 intent = 任务（task）**，四个：

| 意图 | 用户在干什么 | 典型问句 |
|---|---|---|
| `graph_maintenance` | **维护图谱**（Agent 主导） | "我今天跟王五聊了，他说 c 组要并进 b 组" |
| `lead_discovery` | 找线索、判断时机 | "最近有哪些组织在动？""这条现在值不值得投时间？" |
| `path_navigation` | 找引荐路径 | "我怎么够到 C 司的技术负责人？" |
| `outreach_ops` | 触达与跟进 | "王五这条我上次聊到哪了？该跟进了吗？" |

> **为什么必须显式说明这个改动**：登记表的语义一旦从"受众"变成"任务"，
> 后面每加一行的判断标准就不一样了。不写下来，三个月后没人知道该按什么标准加。

**每个意图仍然带自己的**：目标、成功判据、边界、工具白名单、校验器、预算——这套结构照搬阿桥，是它被验证过的部分。

### 4.2 工具清单（按 Agent 干的四件事分组）

#### A. 抽取与写入（Agent 从对话里拿事实）

| 工具 | 风险 | 做什么 |
|---|---|---|
| `graph_reconcile` | **只读** | 传入候选新事实，返回三选一：**新建 / 合并到已有 / 与已有冲突**。**不写库** |
| `graph_apply` | 低 | 把 reconcile 的结果落库。带幂等键，重复调用不产生重复节点 |
| `touchpoint_add` | 低 | 记一次接触：时间、渠道、聊了什么、结果、下一步 |
| `event_record` | 低 | 记一条组织变动事件，**来源与证实状态必填** |

> **为什么把 `reconcile` 和 `apply` 拆成两个工具**——这是本产品最关键的一个结构决定。
> 如果让模型一边判断一边写库，"这两个王五是不是同一个人"就成了一次不可复现的模型判断：
> 同一份数据两次可能给出不同答案，用户的图会随机漂移，而且**没法写测试**。
> 拆开之后，合并/冲突的判定是一个**确定性的、可测试的、可回归的**只读函数，
> 模型只负责把话变成候选事实，以及把冲突讲给用户听。

#### B. 组织与查询（Agent 把图理清楚）

| 工具 | 风险 | 做什么 |
|---|---|---|
| `graph_query` | 只读 | 按公司 / 单元 / 类别 / 时间查节点和边 |
| `org_chart` | 只读 | 某公司的架构树。**残缺就画成残缺**，不补全（§5.3） |
| `path_find` | 只读 | 我 → ? → 目标人，返回最多 3 条最短路径，每跳带关系强度和来源 |
| `stale_scan` | 只读 | 扫出待确认字段、超过 N 个月没更新的关系、悬空的下一步 |

#### C. 情报与线索（Agent 主动去看外面）

| 工具 | 风险 | 做什么 |
|---|---|---|
| `public_source_fetch` | 只读 | **仅限合法公开源**（公司公告、招聘网站 JD、公开新闻、工商变更）。返回原文片段 + URL + 抓取时间 |
| `signal_extract` | 只读 | 从公开源文本里抽出组织变动信号，输出候选 `Event`，**每条必须引用原文片段** |
| `lead_board` | 只读 | 线索看板：按窗口期排序，每条附**它由哪几条信号构成** |

#### D. 触达与合规

| 工具 | 风险 | 做什么 |
|---|---|---|
| `outreach_log` | 低 | 记一次触达及结果 |
| `outreach_plan` | 低 | 排下一次跟进；带节流（同一个人 N 天内不重复提醒） |
| `subject_request` | **不可逆** | 处理被记录人的查询 / 更正 / 删除请求（§6.4）。删除是真删 |
| `graph_forget` | **不可逆** | 删节点 / 整家公司 / 整张图 |

**风险分级的实际含义**：标 `不可逆` 的工具走人工审批——审批与**这一次调用的参数哈希**绑定，
用户看到的就是将要执行的那组参数，不是一句概括。（沿用阿桥 `docs/08-approval.md` 的机制。）

### 4.3 Agent 的维护循环（"整理和更新"具体是怎么发生的）

Agent 有**两条**跑动路径，缺一不可：

#### 路径一：对话中，每一轮都跑（被动）

```
用户说话
  └─ understand : 这轮话里有没有事实？（人 / 组织 / 事件 / 接触）
  └─ plan       : 抽出候选事实 → 调 graph_reconcile 对账
  └─ act        : 有把握的 → graph_apply 直接落库
                   有冲突的 → 攒进「待确认」，不写
  └─ verify     : 校验器跑（来源是否齐、有没有静默覆盖、有没有编造）
  └─ respond    : 正常回答用户本来问的事
                   + 末尾一行回执：「已更新：A 司 c 组 → 并入 b 组（未证实）；影响 3 人」
                   + 最多问一个问题，绝不发问卷
```

**为什么回执只有一行、问题最多一个**：
用户是在干别的事的过程中顺口说了这句话。一个每次都跳出来确认三件事的助手，
第二天就会被绕开——用户会停止告诉它任何事，图随之饿死。
**"不打断"不是体验优化，是这个产品能不能活下来的前提。**

#### 路径二：后台定时跑（主动）

```
每天一次（不占用户的对话轮次）：
  1. public_source_fetch  ← 用户关注的公司清单
  2. signal_extract       ← 抽出候选事件
  3. graph_reconcile      ← 与已有图对账，去重
  4. 生成预警             ← 「c 组并入 b 组；你图上有 3 个人在那里」
  5. stale_scan           ← 「王五这条 6 个月没动了，还准吗？」
```

> **为什么必须有路径二**：只靠路径一，图只会记录"用户已经知道的事"——
> 而这个产品的价值恰恰是**告诉用户他还不知道的事**。
> 没有路径二，它就是个手工 CRM。

### 4.4 冲突怎么处理（Agent 做整理最难的一段）

| 冲突类型 | 例子 | 处理规则 |
|---|---|---|
| **同一实体不同叫法** | "王五" / "王总" / "老王" | `reconcile` 给出合并候选 + 依据（同公司同组同职务），**必须用户确认才合并**。绝不自动合并 |
| **同一字段不同值** | 上次说组长，这次说总监 | **默认解释为"发生了变化"**：生成一条晋升事件，旧值保留在时间轴上。同时问一句"是升了，还是我之前记错了？" |
| **传闻与官方冲突** | 听说要裁撤，公告说是合并 | 官方优先成为当前值，**传闻不删**，留在时间轴上并标注"后被公告推翻" |
| **同一情报重复进来** | 用户说了一遍，新闻里又抓到一遍 | 幂等键 = (来源标识, 实体键)。重复不产生新节点，但**证实状态从 hearsay 升到 corroborated** |

**两条铁律：**

1. **绝不静默覆盖。** 任何对已有字段的修改都留痕、都可回溯。
   > **为什么**：这类系统最致命的失败是——用户几周后基于一个被悄悄改过的事实做了决定，
   > 而且**没有任何痕迹能让他发现**。宁可多问一句，不可静默改一次。

2. **默认解释为"世界变了"，而不是"用户记错了"。**
   > **为什么**：这个产品的全部价值建立在"追踪变化"上。
   > 把变化当成录入错误改掉，等于把产品最值钱的那类数据当垃圾删了。

### 4.5 校验器（verifier）

| 校验器 | 严重级 | 拦什么 |
|---|---|---|
| `source_required` | **阻断** | 任何节点 / 边 / 事件落库时来源为空 |
| `no_silent_overwrite` | **阻断** | 修改已有字段却没有生成变更记录 |
| `score_is_explained` | **阻断** | 输出分数却没有附上构成它的具名信号（§7） |
| `no_sensitive_fields` | **阻断** | 健康、婚育、宗教、政治、金融账户、行踪轨迹等敏感个人信息入库（§6.3） |
| `corroboration_stated` | 修复 | 把 hearsay 说成已发生的事实 |
| `no_scraped_source` | **阻断** | 情报来源指向禁止来源清单里的平台（§6.2） |

## 5. 数据模型

```go
type NodeKind string
const (
    NodeOrg      NodeKind = "org"       // 公司
    NodeUnit     NodeKind = "unit"      // 部门 / 业务组  ← 组织变动的主体
    NodePerson   NodeKind = "person"
    NodeEvent    NodeKind = "event"     // 组织变动。有时间点，追加不覆盖
    NodeLead     NodeKind = "lead"      // 线索。主体是 unit 或岗位，不是人
    NodeOutreach NodeKind = "outreach"  // 一次触达
)

type Node struct {
    ID, OwnerID string          // OwnerID: 归属（个人或团队）
    Kind        NodeKind
    Label, Org  string
    UnitPath    []string        // ["A司","技术中心","c业务组"] —— 架构树的层级
    RoleTitle, Duty string
    OccurredAt  *time.Time      // event
    Intel       []IntelRef      // 支撑这个节点的每一条情报
    Unconfirmed []string        // 哪些字段还没有来源。序列化必须是 [] 不是 null
    History     []FieldChange   // 每次字段变更的留痕（no_silent_overwrite 的落点）
    CreatedAt, UpdatedAt time.Time
}

type IntelRef struct {
    Kind       string    // "user_said" | "public_source" | "team_shared"
    SourceURL  string    // public_source 必填
    Excerpt    string    // 原文片段，不是摘要
    FetchedAt  time.Time
    Corroboration string // hearsay | corroborated | announced
}

type EdgeKind string
const (
    EdgeBelongsTo  EdgeKind = "belongs_to"    // person → unit → org（架构线）
    EdgeReportsTo  EdgeKind = "reports_to"
    EdgeColleague  EdgeKind = "colleague_of"  // 跨公司关系线
    EdgeKnows      EdgeKind = "knows"
    EdgeReferred   EdgeKind = "referred_by"
    EdgeInfluences EdgeKind = "influences"    // 事件 → 线索
)

type Edge struct {
    ID, OwnerID string
    Kind        EdgeKind
    From, To    string
    Strength    int       // 1-3，关系强度。**只能由用户填**，系统不推断（§8.2）
    Context     string    // "2019-2021 在 A 司同一个项目"
    ValidUntil  *time.Time// 组织调整后，旧的隶属边在这里截止，而不是被删掉
    Intel       []IntelRef// 为空 = 这条边非法，store 层拒收
    CreatedAt   time.Time
}
```

**三个刻意的设计决定：**

| 决定 | 为什么 |
|---|---|
| `Intel` 为空的边，store 层直接拒收 | 让"每条线都有来源"成为**存储层的性质**，不是靠调用方自觉。校验器是第二道防线，不是第一道 |
| 组织调整时旧边写 `ValidUntil` 而不是删除 | 三个月后要回答"他当时在哪个组"。删掉就答不出来了，而这正是本产品的核心资产 |
| `unit` 是一等公民节点，不是 person 的一个字符串字段 | 组织变动的主体是**组**不是人。"c 组并入 b 组"必须能一次性作用到组里所有人，字符串字段做不到这件事 |

## 6. 情报来源分级与合规红线（**这一节决定公司会不会出事**）

### 6.1 来源分级

| 级别 | 来源 | 能不能用 |
|---|---|---|
| ✅ 自有 | 用户自己的接触、团队内共享、朋友告知 | 能。标 `user_said`，默认 hearsay |
| ✅ 合法公开 | 公司公告、财报、官方新闻、招聘网站公开 JD、工商登记变更 | 能。必须存 URL + 抓取时间 + 原文片段 |
| ⚠️ 采购 | 第三方联系方式库 | **默认不接**。要接必须先拿到供应商的来源合法性证明与授权链路说明 |
| ❌ 抓取 | 领英 / 脉脉 / BOSS 等平台的简历、动态、通讯录 | **禁止，写死在代码里** |

### 6.2 为什么"抓平台"这条必须写死

它同时踩三样东西，而且**代价是刑事和民事的，不是罚款级的**：

1. **违反平台服务条款** —— 账号封禁、平台民事索赔（国内已有多起判例）。
2. **可能触及《刑法》285 条**"非法获取计算机信息系统数据"——绕过平台反爬措施获取数据。
3. **《个人信息保护法》** —— 抓来的个人信息没有任何合法处理依据。

**所以它不是一个"默认关闭的开关"，而是一份禁止来源清单 + 一道阻断级校验器（`no_scraped_source`）。**
> 为什么不做成开关：开关会被打开。做成清单 + 校验器 + 围栏测试，打开它需要改代码、过评审、留记录。

### 6.3 敏感个人信息一律不入库

健康、婚育、宗教、政治、金融账户、行踪轨迹——**字段层面拦截**，不是"尽量不记"。

> **两个理由，一个合规一个业务**：
> ① 《个人信息保护法》第 28-29 条：敏感个人信息需要单独同意 + 必要性论证，本产品拿不到；
> ② **它对判断根本没用**。加进去只增加风险，不增加成单率。

### 6.4 被记录人的权利通道（`subject_request`）

被记录的人有权查询、更正、删除关于自己的记录（PIPL 44-47 条）。必须有一条真实可走的通道：

- 查询：返回系统里关于他的全部记录及其来源。
- 更正：改，并留痕。
- 删除：**真删**，包括团队共享副本和导出记录里的引用。

> **为什么这不只是合规成本**：这是风控。to B 客户最怕的不是罚款，是一封投诉信让客户的品牌部介入。
> 有一条能立刻走完的删除通道，这件事就停在客服层面；没有，它会一路走到客户的法务。

## 7. 线索评分：可以有分数，但分数必须能被拆开

用户明确要"离职提醒"，也就是要**排序**。这里不回避排序，但对分数有三条硬约束：

### 7.1 评的是"处境"，主体尽量是组织单元，不是人

```
c 业务组 · 稳定性信号                                    窗口期 ~3 个月
  ├ 并入 b 组（8/29 · 公告）                                    +++
  ├ 该组 6 个月无新增招聘（招聘网站 · 9/1）                        ++
  └ 组长上季度公开分享过团队规划（公开动态 · 6/12）                  −
  图上你认识 3 个人：王五（组长）、张三、李四
```

> **为什么主体是组不是人**：组织级信号**推不出**个人意图。
> 硬推出来的"王五 87% 会离职"是编的——猎头拿去用，第一句话就会露馅，转化率反而更低。
> 个人级分数只在有**个人级信号**时才成立（本人公开表达、简历更新、公开求职），而这类信号本来就少。

### 7.2 分数必须附带构成它的具名信号（`score_is_explained` 阻断级）

界面上永远是"因为这几条"，不是一个孤零零的数字。

> **为什么**：猎头要用这个分数决定今天打哪通电话。一个黑箱数字既没法验证也没法反驳，
> 用错了还没法归因。可拆开的分数才是能改进的分数。

### 7.3 分数不进导出、不进 API、不出现在给候选人看的任何地方

> **为什么**：一份"离职可能性排行榜"外流的后果，远不止是尴尬——
> 榜上的人可能因此在自己公司里出事。这条要在导出和 API 两层各拦一次。

## 8. 图谱与路径视图

### 8.1 三个视图

| 视图 | 回答什么问题 | 形态 |
|---|---|---|
| **组织架构图** | "A 司这个组都有谁？" | 层级树。已知实线、听说虚线、**不知道就空着**（不补全，§5） |
| **关系图谱** | "谁跟谁认识？" | 力导向图。分类 chips、拖拽、缩放、点击看详情（参考人生图谱的交互） |
| **引荐路径** | **"我怎么够到他？"** | 从我出发的连接链，最多 3 条，每跳带关系强度和来源 |

### 8.2 引荐路径是这个产品最值钱的视图

```
你 → 张三（前同事，强）→ b2（张三在 C 司的同事，中）→ 王五（目标）
                                                    2 跳可达
你 → 李四（微信群认识，弱）→ 王五                        1 跳，但关系弱
```

> **为什么它比"离职预测"更值钱**：
> ① 它建立在**你自己的关系记录**上，没有任何第三方数据风险；
> ② 它直接决定回复率——"张三让我联系你"和陌生开发信是两个数量级；
> ③ 别人抄不走。竞品能买到同样的人才库，买不到你的关系网。
>
> **`Strength` 只能由用户填，系统不推断。** 系统推不出"你跟这个人有多熟"——
> 硬推的结果是把一条弱关系当强关系用出去，尴尬的是用户本人。

### 8.3 图谱必须能降级

低带宽 / 渲染失败时，退回文字版分组清单，**功能不缺失**。
图谱是展示层，它不产生任何新信息——这一点在排期上很重要（§9）。

**P2 的四个判定与四个答复**

| 判定 | 含义 | 谁能落库 |
|---|---|---|
| `create` | 图上没有像它的东西 | Agent 直接落 |
| `update` | 完全同一条记录，且没有任何值相抵触 | Agent 直接落 |
| `merge` | 按具名规则像某条已有记录 | **必须人答** |
| `conflict` | 同一条记录，某个值不一样 | **必须人答** |

四个答复：`create_new`（是两个人）/ `merge_into`（是同一个）/ `accept_change`（世界变了 → 落值 + 生成事件）/ `keep_current`（那个说法不对 → 不改值，但把"有人这么说过、被驳回"写进时间轴）。

**合并候选的三条具名规则**（每条都要**两个**信号，绝不靠单一弱信号）：

| 规则键 | 触发条件 |
|---|---|
| `same_org_same_unit_shared_surname` | 同公司 + 同组 + 同姓 + 一个称呼是另一个的缩写（王总 → 王 是 王五 的前缀） |
| `same_org_same_role_shared_surname` | 同公司 + 同职务 + 同姓 + 称呼可缩写 |
| `same_org_label_contained` | 组织/单元：同公司 + 一个名字包含另一个（c业务组 / c组） |

> 为什么"王五 vs 王六"不算候选：同姓在任何中国公司都能匹配三分之一的人，是弱信号。
> 规则要求"一个称呼是另一个的缩写"，王五和王六互相都不是前缀，所以是两个人。

**P3 的三条硬约束**（一条不能少，少任一条这个功能就废了）

| 约束 | 为什么 |
|---|---|
| 一轮**最多一个问题** | 用户是在干别的事时顺口说了那句话。每次跳出来确认三件事的助手，第二天就被绕开 —— **图饿死才是这类产品的死法** |
| 没记下东西就**不出回执** | 每轮都有回执 = 噪音，噪音会让"一行回执"变成用户学会跳过的东西 |
| 安静**不等于**放行 | 这轮没空问的判断**一条都不落库**，全部进队列，下轮继续等 |

**两个排序决定**：

1. **冲突优先于合并。** 冲突意味着图上现在存着一条被用户自己刚说的话推翻的事实——不问，下一次回答就会引用一条他刚纠正过的事实，这是最快丢掉信任的方式。而未解决的合并只是多一条重复记录：看得见、无害、以后能修。
2. **问过一次没答的，下一轮不再问。** 用户没答的问题第二次并不会更紧急；重复问是唠叨，唠叨会训练用户忽略这个通道。（`PendingItem.Asked`）

**队列是按席位的，不是按团队的。** 问题是关于这个人自己那次对话的，一个没听过那场对话的同事去回答，比没人回答更糟。顾问离职时队列随他一起删除 —— 留着是一份只会增长、没人能答的积压。

**"算了" 和 "我决定了" 是两个 API**（`DropPending` vs `Answer`），这样"我不想决定"永远不会在记录里被当成"我决定了"。

**P4 的核心不是画树，是把"不知道"画出来**

一棵看起来完整的组织树会被读成"系统知道这家公司的结构"，而其中凡是用户没说过的部分**都只能是编的**。所以：

| 规则 | 落点 |
|---|---|
| 不凭空造层级 | 树只由**有人说过的路径**构成：已记录的 unit 路径 + 能放进去的人的路径。中间不插值 |
| 只被提过的层级标 `mentioned` | 界面画虚线；它有名字，但我们手上没有关于它的任何东西 |
| 放不进去的人**列出来** | 一个被悄悄丢掉的人，和一个不存在的人，在页面上长得一模一样 |
| 同名两处报歧义，不合并 | "c业务组"出现在两个深度：可能是同一个组，也可能是两个组，都可能，所以说出来而不是挑一个 |
| 计数来自树本身 | 从别处算的汇总，就是"9 个人的列表上面写着 12 人"的来源 |

**一条我特意加的规则：已截止的隶属关系，不回落到人身上那条路径。**

组织调整后 `belongs_to` 边被 `CloseEdge` 截止，但这个人自己的 `UnitPath` 字段还写着老组。如果找不到有效隶属就回落去读那个字段，**就会把他放回他刚离开的组** —— 而那正是有人要根据这张图去联系他的时刻，是这张图能犯的最贵的错。所以规则是：**只要他有过隶属关系，就只认还有效的那些**；全截止了就是"不知道他现在在哪"，并附上截止日期。围栏 `TestEndedMembershipDoesNotFallBackToTheOldGroup` 同时验证"调整后不在旧组"和"调整前的历史仍然答得出来"。

**`Roster`（文字版分组清单）是从 `OrgChart` 推导的，不是另查一遍。** 它们回答同一个问题，各写一份两次改动之内就会不一致；而它是图谱视图在低带宽 / 渲染失败时的兜底 —— **一个和它所替代的东西说法不一致的兜底，比没有兜底更糟**。它还保留了"已记录 / 只被提过"的区分：兜底不能显得比原件更确定。

**P5：路径从哪里起算 —— 这个问题只有一个诚实答案**

图里没有"我"这个节点（图存的是外部的人，不是团队自己）。所以"我能去问谁"必须从用户**说过的东西**里推导，而这个模型里只有一样东西是用户亲口说的：**关系强度**。

于是 `Strength` 从装饰变成了承重结构：**标过强度 = 我认识他 = 可以作为路径起点**。顺带让空状态变得诚实：

| 空结果 | 含义 | 下一步 |
|---|---|---|
| `NoSeeds = true` | 你还没标过任何人的关系强度 | 告诉我你认识谁 |
| `Paths` 为空 | 你认识的人里没有一条连得上他 | 换个人问 / 扩大跳数 |

这两种在屏幕上长得一模一样，但补救方式完全不同，所以必须分开。

**排序：最弱一环优先于跳数少。** 一条链条的强度取决于最弱那一环——通过一个不太熟的人的 1 跳，比通过两个熟人的 2 跳更差。先给短的那条，就是让用户挑一条走不通的路。围栏 `TestStrongerWeakestLinkBeatsFewerHops` 专门构造了这个对照。

**只走关系线，不走架构线。** 汇报线 / 隶属线是结构，不是"这个人会帮我引荐"。把汇报线当温路径，正好会产出那种让托人的人尴尬的引荐。

**Q1 的一个直接后果**：别人跟别人有多熟，你看不到（强度是席位私有的）。所以路径里不属于你的那一跳 `Mine=false`、`Strength=0`，界面要说"这一跳不是你自己的关系"，而不是显示一个看起来很确定的 0。

**接触记录（touchpoint）：为什么是团队的**

「上周有人已经打过他电话了」是**唯一**能阻止两个顾问一周内先后 cold-call 同一个人的事实——而那正是让公司在它最想打动的人面前显得没组织的失误。它必须在打电话那个顾问离职之后仍然存在。所以：**记录归团队，只有上面那条私人印象归席位**。

字段上也照这条切：`Topic` / `Outcome` / `NextStep` 是**事实**（说了什么），归团队；"他听起来很敷衍"是**判断**，进 `Note`（私有）。

**一个刻意的例外：接触记录不要求 `Intel`。** 其他所有记录都必须说明来源，因为它们是关于第三方、会被人拿去行动的断言。接触记录**本身就是它自己的来源**：`SeatID` 说是谁、`At` 说什么时候、`TurnRef` 指向那轮对话。没有外部出处可引，因为出处就是填它的人。

**移除了 `KindOutreach` 这个占位枚举。** 它从来没有生产者也没有消费者，而现在真正的 `Touchpoint` 类型接手了这件事。一个占位枚举会被读成"机制已经在那儿了"，从而悄悄吃掉本该用来建它的注意力。

**⚠️ P5 抓到两道真空围栏（绿的测试证明不了保护存在）**

1. **变异打错了地方**：我删掉的是 `myStrengths` 里的 `TeamID` 判断，但真正的机制是"只读 `s.notes[v.SeatID]` 这一个席位的表"。换成"遍历所有席位"之后，`TestAHopThatIsNotYoursIsMarkedNotScored` 立刻变红 —— 围栏是真的，之前是我的尺子错了。
2. **代码里有冗余分支**：`buildPath` 里 `if !h.Mine { Weakest = 0 }` 和后面的数值比较**永远等价**（没标过的跳强度就是 0），删掉它测试全绿。这比没有围栏更糟：它读起来像一道保护，实际什么也没保护。已合并成一条规则一行代码，并把这段经过写进注释。

**P6 + P9 一起做的原因：它们共用同一份记录**

P6 要知道"上次这个源说了什么"才能发现某个组不再招人；P9 要知道"这条事实从哪来"才能回答主体查询。这是同一张表：**每次抓取一行，无论有没有产出**。

> **保留"什么都没产出"的那些行才是关键。**「我们看过了，没有」和「我们从来没看」是两个不同的答案，只有台账分得清。

**P6 的三条**

| 规则 | 为什么 |
|---|---|
| 禁止来源**在发请求之前**就被拒 | 只在存储层拒绝已经太晚了：那时爬取已经发生、对方的日志已经存在、ToS 已经违反。所以 `Source` 必须声明它会访问哪些 host，声明里带禁止 host 的源**一次请求都不会发出**。返回结果里再查一遍 URL 是纵深防御，不是主闸门 |
| 招聘广告产出 `unit`，不产出 `event` | 一条招聘广告说明这个组存在、在招人；它**没有说发生了什么**。硬把它变成事件就是制造新闻。真正的信号是**时间上的缺席**（`HiringGap` 从台账算），不是从一条广告里猜 |
| 工商变更 / 公司公告 = `Announced` | 这是公司自己在说话，是本包里**唯一**产生"官方公布"这个等级的地方 |

**预警：只说两件用户已经告诉过我们的事**

「A 司 c 组并入 b 组（公告）+ 你图上在 c 组的有 3 个人」。没有分数、没有排序、不预测任何人的去留 —— 这正是 PRD §5.7 那条边界的落点。而且**一个事件只预警一次**：重复提醒等于催促行动，这个功能的定位是"别错过"，不是"快去联系"。

预警里"谁在那个组"直接复用 P4 的架构树，所以它自动继承了"已截止的隶属不回落到旧组"那条规则。

**P9 的四件事**

| 能力 | 落点 |
|---|---|
| 敏感字段闸门 | 健康 / 婚育 / 宗教 / 政治 / 金融证件 / 行踪 六类词表，**在写入时拒绝**，所有接受自由文本的路径都接了（节点、边、接触记录、私人备注） |
| 来源台账 + `Provenance` | 任一条记录都能回答"从哪来"：证据本身 + 背后的抓取行 + 全部变更历史 |
| `SubjectRecords` / `ForgetSubject` | 主体查询与删除，**跨团队** |
| `Export` + 审计 | 导出只带自己的备注；导出、主体查询、主体删除、被拒抓取都留审计 |

**三个需要你知道的判断**

1. **`SubjectRecords` 是本包里唯一跨团队的读，而且不接受 `View`。** 一个人的权利是关于他自己的，不是关于我们的租户模型；让他先说出"可能哪几个团队存了我"是不可能的，只答一个团队就是答错。它是**运营动作**，每碰一个团队就写一条审计。
2. **私人备注会交给主体本人。** 这是真实的张力——顾问的私人判断变成可披露的，会改变他愿意写什么——这里按法律的口径判给主体。**建议找法务确认后再定稿。**
3. **敏感词表的误伤是明说的取舍。** "残疾证办理专员"是真实岗位。所以词表刻意**窄而具体**（多字、难以无辜使用的词），不用"病""残疾"这种裸词；误伤时报错会**指名是哪个词、哪一类**，让用户一次改对而不是猜。**加宽这张表是产品决策，不是 bug fix。**

**~~‼️ `RunDaily` 的排队分支没有生产者~~ → 已修复 2026-09-10。根因比原先判断的更严重。**

原先的判断是"抽取器设置的字段都在自然键里，所以不可能冲突"。**这个判断是错的**：真正的问题是路径二会**静默产生重复记录**。

用户把「c业务组」记在 `技术中心` 下面，招聘广告推出来的「c业务组」在公司下面 —— 不同的 UnitPath ⇒ 不同的自然键 ⇒ store 正确地拒绝把它们当成一条。但 `Reconcile` 在找合并候选时**跳过了所有同名节点**，理由是"同名必然是精确键命中，调用方已经处理了"。**这个假设是错的**（键里还有路径）。结果就是悄悄多出一份记录、没人被问 —— 这正是 P7 走查里同一个组上榜两次的根因。

已修：新增规则 `same_org_same_label_other_path`（同公司 + 同名 + 不同位置 ⇒ 合并候选，任何 kind 都适用），排队分支随之有了生产者并被 `TestTheDailyPassParksTheDecisionsItRaises` 覆盖 —— 该用例同时验证"不静默新建"、"排进队列"、"问题带出理由"、"本人答完只剩一条记录"。

**P8：图谱是叠加层，文字才是页面**

架构是这样定的：**服务端把文字版清单直接渲染进 HTML**，图谱是脚本在它上面叠的一层增强。

> 一个需要先取数、再渲染才能出现的"兜底"根本不是兜底 —— 它恰好在它该起作用的那些条件下失效。

所以：没有脚本、链路慢、渲染出错、打印页面，读者拿到的仍是每个人、每个组、每个"待确认"角标。围栏 `TestThePageCarriesTheRosterWithoutAnyScript` 把 HTML 在**第一个 `<script>` 之前**截断，断言这些内容已经在里面了。

**视觉只编码事实**（PRD §09 那条规则的落点）：

| 编码 | 含义 |
|---|---|
| 颜色 | 节点类别 |
| 虚线圈 | 只被提过、没有记录的组 |
| 虚线 | 未证实的关系 |
| **大小** | **恒定 —— 什么都不编码** |

围栏 `TestNothingOnTheGraphEncodesImportance` 直接读发布出去的 `graph.js`，断言半径只来自常量 `R`、线宽不来自任何 strength/weight/score；`TestTheSnapshotCarriesNoRanking` 再断言 payload 里根本没有 `score`/`rank`/`weight`/`size` 这些键 —— **数据里没有，未来任何一版样式表都没法开始编码它**。

**布局先算完再画。** 力导向如果只在 `requestAnimationFrame` 里收敛，它就只在标签页可见时收敛：渲染进隐藏标签、打印、截图或被节流的后台，它画完第一帧混乱状态就停 —— 而那一帧看起来像一张画完的图。所以模拟在**第一次绘制之前**同步跑完，拖拽时局部重算，没有任何自走的动画（`prefers-reduced-motion` 也就不需要特例）。

**认证是宿主的事。** `Handler(store, resolve)` —— `resolve` 把请求变成一个 `View`，解析不出来就 401。在这个包里发明一套 header/cookie 方案，等于把安全决策做在错误的地方然后被依赖。

**‼️ 界面走查抓到两个真 bug（这就是为什么验收标准里写了"走查"）**

1. **预警说"你图上这个组还没有人"，而那个组里有 3 个人。** 事件只知道 `公司 + 组`（抽取器就这点信息），而用户把那个组放在了更深的位置（`A司 › 技术中心 › c业务组`）。按整条路径匹配，**恰好在用户告诉了我们更多结构的时候找不到人** —— 方向反了。改成按组名匹配（同名出现在两处会两处都命中，而那个歧义架构树本来就单独报了）。
2. **图上根本没有架构线，只有关系线。** 一个没被记录过的层级（技术中心）在图上**完全不存在**，于是 PRD 承诺的"架构图 + 关系线"只做了一半 —— 更糟的是，**图看起来比它本该更丰富的那个文字清单还要整洁**。已补：架构树的层级和人-组归属都进图，只被提过的层级作为虚线框节点（id 带 `mentioned:` 前缀，一眼能看出它不是记录），并且这些线标记为 `Derived`，绝不和"有人记录过的隶属"混为一谈。

**一个设计观察，需要你知道（不是 bug）**：在真实数据里**几乎所有线都是"未证实"**（大多数事实来自一次对话、单一来源），所以虚线会变成默认样式、失去区分度。当前是诚实的，但视觉上信息量低。P7 之后可以考虑把"已证实"做成更明显的正向标记，而不是靠"没有虚线"来表达。

**P7：三条硬约束，每条都做成"结构上不可能违反"，而不是事后检查**

| 约束 | 落法 |
|---|---|
| ① 主体是**组**不是人 | `Lead` 类型里**根本没有 person 字段**。人只作为"你在这个组认识谁"出现，且按姓名排序 —— 一旦那份名单按别的排，产品就又在给人排名了 |
| ② 分数必须附带构成它的具名信号 | **`Score()` 是方法，不是字段** —— 它由 `Signals` 求和得出。于是"持有一个没有证据的分数"这件事**在类型上就不存在**，也没有任何未来的代码路径能忘记附上证据。一道校验器只是它的弱化版 |
| ③ 分数不外流 | 榜单**只由服务端渲染进 HTML**，不进 `/data`（机器可读接口），不进 `Export`。两个出口各一条围栏 |

**权重是一张表，不是散落的条件分支。** 每个数字都在界面上紧挨着它的来源；散进 if 里，恰好会让榜单在有人不同意它的时候解释不清 —— 而那正是解释存在的意义。事件的权重随证实等级上升（公告 3 / 多源 2 / 听说 1）：**如果一份公告和一条传闻等重，追踪证实等级就只是装饰**。

**窗口期自带定义。** 界面上写的是"窗口期约剩 77 天（自最近一条信号起算 90 天）"——90 天是一个**约定**不是测量，所以它印在数字旁边。一个需要读者信任的数字不是一个被解释过的数字。

**‼️ 走查又抓到两个（第二次证明"跑测试 ≠ 走查"）**

1. **同一个组在榜上出现了两行**，一行带人一行不带 —— 因为"c业务组"在图上有两个位置（用户说的那个在 `技术中心` 下面，招聘广告推出来的那个在公司下面）。榜单原本是"每个图节点一行"，而它应该是**每个"情形"一行**：事件说的是"A司的c业务组"，这样的情形只有一个，不管这个名字在图上出现几次。已改为按 `(公司, 组名)` 合并、人去重、信号只算一次，并在行上注明"这个名字在图上出现在 2 个位置，可能是同一个组"。
2. **Go 代码里写了英文界面句子**（`"no advert seen for 240 days"`）出现在一个全中文的页面上 —— 我自己在 P3 定的规矩（回执带计数不带散文）被自己破了。已改为信号只带 `Kind` + `Days`，句子由模板渲染。

顺手两处用词：`0 天前还在招人` → `今天还在招人`；标题从"值得现在投时间的"改成**"线索看板 · 按分数排序"** —— 因为一个 **−1 分的行**（这个组还在招人 = 没动静）挂在"值得现在投时间的"底下是自相矛盾。那行本身有价值（决策时需要知道"这里没动静"），所以留下行、改掉标题。

**收尾：给模型用的工具层（原先标注为缺口，已补齐）**

`internal/leadgraph/tool.go` —— 11 个工具，四组齐全（抽取写入 / 组织查询 / 情报线索 / 触达合规），每个都带 JSON Schema、风险等级和实现。

| 保证 | 落法 |
|---|---|
| 模型不能塞进没承诺过的字段 | 所有对象 `additionalProperties:false`，且**校验在进入 `Run` 之前**。一个带 `匹配度` 的调用在门口就被拒，而不是进到函数里等人记得检查 |
| 不可逆操作必须有人点头 | 审批令牌带**这一次调用参数的哈希** —— "同意删除某个东西"不等于"同意删除这一个"。给另一条记录的审批放不了这一条过 |
| 只读的工具不需要审批 | 给读也加闸门会训练调用方"什么都批"，那样审批就不再意味着任何东西 |

**一处如实记录的成本**：这个包**自带了一份 JSON Schema 子集**（约 150 行），没有复用兄弟产品的 `internal/tools`。因为那样会把它的 consent scope、role 和意图登记表一起拖进来 —— 正是 PRD §01 说明不复用的东西。**这是已知的重复**，也是 Q4 一旦拍板拆仓时第一个该抽成共享库的部分。写在这里，免得日后被当成疏忽发现。

**实现决定汇总**（PRD 里没写，需追认）：

1. **`Actor`（user / agent）进入存储层签名。** 三条规则对人和对 Agent 解析不同（关系强度只有人能写、已有值只有人能改、冲突只有人能裁），做成运行时可测的机制，而不是注释。
2. **`Corroboration` 改为派生而非存储。** 由记录上的 intel 现算：任一官方来源 → 官方公布；≥2 个不同来源 → 多源印证；否则听说。避免存字段与证据脱节；同一来源重复不算印证。
3. **`FieldChange` 加了 `Rejected` 标记。** 用来记"有人这么说过，我们判定它不对"——值没变，但传闻留在时间轴上（对应 PRD §05.4 第三行"传闻不删"）。
4. **`MergeNodes`（合并两条已存在的记录）单独成 API，且对 Agent 完全禁止。** 它是本包唯一真正破坏性的操作：一个 id 会消失。理由不是 Agent 认重复认得差，而是**错了不可恢复**——两个人变成一个，且"曾经是两个"的证据随被删记录一起没了。
5. **`Reconcile` 只处理节点，不处理边。** 边是精确键（kind+from+to），不存在"这两条边是不是同一条"的模糊问题；唯一会冲突的字段是 `Context`，走既有的"Agent 不能覆盖"那条路。
6. **回执做成结构体（计数 + 最多 3 个条目），不是一句中文。** 句子属于界面和它的语言；Go 代码里放中文句子会让以后接国际化时要满仓库找字符串。条目自带 `Corroboration` 和 `Unconfirmed`，这样那一行可以写"未证实"而**不需要**界面再去查一次——也就不会忘。
7. **P3 不含"接触记录"（touchpoint）。** PRD §05.2 的 `touchpoint_add` 还没实现——当前模型里没有这个概念（`outreach` 节点类型占了位）。**标注为缺口**，建议随 P5（引荐路径）一起做，因为那时才需要"上次谁联系过他"。

## 10.2 批量导入的格式要求

**核心原则：适配你的表，不要求你改表。** 一个要求用户先把列名改成模板的导入，等于"先做数据清洗再用产品" —— 没人会做。

### 只有一条硬要求

**第一行必须是表头。** 除此之外，读不懂的文件**不拒收，而是暂存下来让人看**。

> **"整个文件拒收"就是把"先做数据清洗再用产品"挪到了失败之后。** 一个读不懂的文件应该是一次对话，不是一次拒绝：系统暂存它，连同表头和前 5 行样例，让 agent 看着提议"第 1 列看起来是姓名（前三行是王五/张三/李四），对吗？"，用户确认之后**整份文件重读一遍**。

`Blocked` 状态说明卡在哪（目前只有"认不出姓名列"和"没有数据行"两种），**被阻塞的计划落不了库**。

### 自动处理的

| 项 | 说明 |
|---|---|
| 编码 | UTF-8 / UTF-8 BOM / **GBK** —— 中文 Excel 另存为 CSV 默认就是 GBK，**这是"导入成功但全是乱码"最常见的来源** |
| 分隔符 | 逗号 / 制表符 / 分号，按表头行里出现最多的那个 |
| 参差不齐的行 | 手工维护的表里很正常，不报错 |
| 不规范引号 | 宽容解析 |

### 认识的列名（别名表；忽略大小写、空格、下划线、连字符）

| 字段 | 认识的写法 |
|---|---|
| 姓名 | 姓名、名字、人名、联系人、候选人、name、full name、contact |
| 公司 | 公司、单位、所在公司、企业、雇主、现公司、company、organization、employer |
| 部门 | 部门、团队、业务组、事业部、组、department、team、division、unit |
| 职务 | 职务、职位、岗位、title、position、role |
| 职责 | 职责、负责、分管、工作内容、responsibility、scope |
| 熟悉程度 | 熟悉程度、关系强度、亲密度、熟悉度、关系、strength、closeness |
| 备注 | 备注、说明、补充、note、notes、comment |

**不认识的列会被列出来报给你**，不会静默丢弃 —— 一列手机号悄悄消失，和"导入完成"是两件事。

### 强烈建议带上的两列

- **公司**：没有它，所有人都落到"未归组"，而且同名的人分不开（合并判定的两个信号少一个）
- **熟悉程度（1-3）**：**有它，`path_find` 当天就能用；没有它，导入完图上一条起点都没有**。这是导入最值钱的一列 —— 一个顾问愿意说出"我到底跟谁熟"的唯一时刻，就是他在导入那份列着这些人的表的时候

### 两阶段，默认不写

`PlanImport` 只算不写，给出：新建 X / 更新 Y / **需要你决定 Z** / 跳过 W 行（附行号和原因）。`ApplyImport` 才落库。

### 行级容错（一个坏格子不该毁掉整个文件）

| 情况 | 处理 |
|---|---|
| 没有姓名 | 跳过该行，报行号 |
| 熟悉程度不是 1-3 | **该行仍然导入**，只是没有强度；报行号和原值 |
| 某格命中敏感词 | **只丢那个字段**，不是整行、更不是整个文件；报行号 + 列名 + 命中的词。整份拒收会逼用户盲删一列再试一次 |
| 疑似已有的同一个人 | **不静默新建**，变成一条"需要你决定"，走和对话路径完全一样的合并机制 |

### 一个文件 = 一个来源

同一份表里 200 行都说同一件事，证实等级**仍然是"听说"**。否则一份表格就能把自己抬成"多源印证"。（实现上：`TurnRef` 记的是文件，行号在 `Excerpt` 里。）

### Agent 在导入里做什么、不做什么

**它产不出文件** —— 上传是用户的动作。所以形状是：**用户上传 → 系统出计划 → agent 讲解并陪着走 → 用户拍板 → 落库**。

| Agent 能做 | 工具 | 风险 |
|---|---|---|
| 把计划讲成人话（怎么读的、用了哪些列、忽略了哪些、会新建多少、哪些还要你定、跳过了哪几行为什么） | `import_summary` | 只读 |
| 追问"这些人里你最熟的是哪几个" | `rating_gap` | 只读 |
| 记下用户说的熟悉程度 | `rate_contact` | 写 |
| 落库 | `import_commit` | **不可逆 · 需审批** |

**为什么落库是"不可逆"级**：转达一条合并决定是聊天；一次性转达两百行的决定是另一回事。它拿和删除同级的闸门 —— **审批绑定的是这一次调用的全部参数，包括里面每一条决定**。所以"同意导入这份表"**不等于**"同意把第 3 行并进王五"，围栏 `TestTheApprovalCoversTheDecisionsNotJustTheFile` 守着这条。

### 导入的待办**不进**对话队列

`RecordTurn` 一轮最多一个问题，是因为**用户在干别的事**。而导入是**用户正盯着屏幕**的时刻 —— 12 条决定应该在一个 review 屏上一次过。

两个共用一条队列会两头不讨好：对话被 12 个它本来设计成永远不会问的问题淹掉，或者导入要聊 12 轮。所以是**两套结构**，围栏 `TestImportDecisionsStayOutOfTheConversationQueue` 断言导入之后对话队列仍然是 0、下一轮对话也不会被打断。

**暂存的计划只在内存里**，没有新建表。一次 review 就几分钟；为了"进程重启"这种情况建表 + 迁移 + 生命周期，换来的补救是"重新传一次文件"（几秒）。等 review 变成长流程再持久化，现在不。

### 出问题时 agent 怎么修

`import_remap` 一个工具，四种修法 —— **全部是"用户确认之后由 agent 转达"，不是 agent 自己猜**：

| 修法 | 场景 | 例子 |
|---|---|---|
| **改列映射** | 别名表不认识用户的叫法 | `客户名称` → 姓名；表头空白时可以按位置 `#1` |
| **翻译取值** | 文件用的是用户自己的词汇 | `很熟`→3、`一般`→2。**这不是缺陷，是他就这么写的** |
| **补单元格** | 某行缺了姓名 | 用户说"第 4 行是李四" → agent 转达。**agent 不许自己编** |
| **排除行** | 用户说这几行不要 | 第 3 行忽略 |

**修改是"整份重读"，不是"打补丁"。** 每一次修改都从**原始字节**重新读一遍全文件 —— 所以不存在"修了一半的计划"，用户看到的永远是一份完整连贯的读法，改三次也不会攒出一个谁也说不清的状态。围栏 `TestCorrectingTwiceRereadsRatherThanAccumulates` 验证：再发一次空的修改，文件会回到最初的状态。

**修改仍然过所有闸门**：敏感值补不进来（`TestARepairCannotSmuggleSensitiveInformationIn`）；指向一个不存在的列名会被**忽略**而不是悄悄读成第 0 列；只有上传的那个席位能改。

**为什么 `import_remap` 是"写"不是"只读"**：它改的是暂存的读法，**不写图**。所以它不需要审批 —— 审批在后面的 `import_commit` 上，覆盖的是它产出的那份读法。

**文件大小上限 8MB**，超了直接报错并说明限额（不是收下然后忘掉）。

### ‼️ 导入之后必须有人问那一句

导入 200 个人、一条熟悉程度都没标 → **图是满的，`path_find` 仍然返回 `NoSeeds`**。这个包里**没有任何别的东西会去问**，所以 `RatingGap` 就是干这个的：

- 报出"已标 X 人 / 未标 Y 人"，外加**最多 10 个**名字（10 个是人会回答的清单，200 个是人会关掉的清单）
- **名字按姓名排序，不按任何别的东西排。** 那个看起来很贴心的排法——"谁连着的边最多、谁能打开最多路径"——**就是换了顶帽子的给人排名**，而且用户比图更清楚自己跟谁熟

### 联系方式 ✅ 已拍板 2026-09-10：**存**

**归谁：团队。** 它是事实不是判断，按 Q1 的口径就归团队。而且这条本身就是团队模式的意义所在 —— 「上周有人已经打过他电话了」，而**没有号码谁也打不了下一个**。联系方式若按席位私有，同事看得见那通电话、却够不到那个人。

| 认识的列 | 写法 |
|---|---|
| 手机 | 手机、电话、手机号、联系电话、联系方式、phone、mobile、tel、cell |
| 邮箱 | 邮箱、邮件、电子邮箱、email、mail |
| 微信 | 微信、微信号、wechat、weixin、wx |

**四条规则：**

1. **只增不改。** 人有两个号码 —— 第二个不是对第一个的否定，所以联系方式是**集合**、并集合并。于是"Agent 不能覆盖已有值"那条规则在这里根本不会触发：**Agent 只可能新增**。同一个号码写成 `138-0000-0000` 和 `13800000000` 是同一个（手机去标点、邮箱转小写）。
2. **删除只有人能做，且留痕。** 加一个错号码是"多了一条、看得见"；**删掉唯一对的那个，是团队悄无声息地失去联系方式**。所以删除是人的决定，走 `contact_remove` 转达，并在 `History` 里留 `contact:phone` 的记录。
3. **仍然过敏感词闸门。** 手机号在 PIPL 下是**普通**个人信息，`身份证号` 是**敏感**的 —— 而联系方式列正是身份证号最容易被粘进来的地方。导入时命中敏感词**只丢那一条联系方式**，不丢整行。
4. **导出要数它。** 泄漏之后第一个问题是"谁拷走了"，第二个是"里面有多少个能打通的号码" —— 节点数回答不了第二个，所以 `AuditExport` 单独计 `contacts`。

**主体权利自动覆盖**：`SubjectRecords` 会把号码交给本人（他有权知道我们存了），`ForgetSubject` 连带删除。

**没有新建表**：联系方式在 `lead_nodes.doc` 这个 JSONB 里，**零迁移**。

## 11. 待拍板

### 1. 团队共享怎么做？ ✅ **已拍板 2026-09-10：事实归团队，关系强度和私人备注归个人**

**落地形态**：不是过滤，是**两条记录**。事实存在 `lead_nodes` / `lead_edges`（团队可见），
判断存在 `lead_annotations`（`seat_id` + `target_id` 为主键，只有本人读得到）。

**为什么不是"共享表加一列 + 查询时过滤"**：
"同事看不到你的私人备注"如果靠每一条 SELECT 记得排除，只要有一个 join 忘了就不成立。
放进另一张按 seat 键的表，那个 join 根本不会被写出来。

**顺带解决了顾问离职**：`ForgetSeat(seatID)` 删掉他的整套判断，团队的事实一条不动 ——
围栏 `TestSeatDepartureLeavesTheFacts`。

**单人 = 一人团队**，不做"个人模式 / 团队模式"两套分支。

### 2. 公开源从哪几个开始接？

建议第一批只接**工商变更 + 招聘网站公开 JD**：结构化程度高、合法性清楚、信号密度高
（一个组停止招聘，本身就是强信号）。新闻和公告的抽取难度高一档，放第二批。

### 3. 个人级评分要不要做？

§7.1 建议主体是组织单元。若一定要做个人分，需要先回答：**个人级信号从哪来？**
如果答案是"从平台抓"，那就回到了 §6.2 的禁止项 —— **这条会决定整个产品的合规姿态**。

### 4. 与阿桥的代码关系：同仓复用，还是独立仓？

- **同仓**：复用图存储和 Agent 循环最省事，但两个产品的边界会互相污染（阿桥禁止打分，这里必须打分）。
- **独立仓 + 抽公共库**（推荐）：把 store / agent loop / guardrail 框架抽成共享库，两个产品各自持有自己的意图和校验器。
