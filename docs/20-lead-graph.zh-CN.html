01为什么它是独立产品，而不是阿桥的一个功能

阿桥（Opportunity Bridge Agent）的底线是不认定资格、不给人打分。本产品的核心恰恰是给组织和岗位打分排序、判断什么时候该联系谁。这两件事不能装在同一个意图登记表里——装进去就等于把阿桥那套边界推翻，而那套边界是它对用户的承诺。

复用不复用
图存储、幂等写入、迁移规范阿桥的意图登记表 internal/intent
Agent 循环 understand → plan → act → verify → respond阿桥的五个意图及其边界
校验器框架 internal/guardrailno_candidate_scoring 等禁止打分的校验器
人工审批机制（参数哈希绑定）面向居民的授权范围模型
为什么要写下这条

把两个价值观相反的产品塞进一个仓库，最先坏掉的不是代码，是判断标准：下一个人加功能时，不知道该按哪套边界来审。文档里留下这张表，是为了让"该不该复用"这个问题有一个可查的答案，而不是每次重新吵一遍。

02核心洞察：值钱的是时机和路径，不是名单

主流工具（领英、Apollo、各类简历库）卖的是人的静态档案——联系方式、履历、技能。这类数据是同质的：谁都买得到，谁都在发同样的开发信，回复率被打到地板。

真正决定成单的是两件档案里没有的东西：

变量为什么它决定成败
时机同一个人，组织重组后的三个月和平常的三个月，接电话的概率完全不同
路径陌生开发信 vs「张三让我联系你」，是两个数量级的回复率差距
为什么这构成壁垒

本产品的两个核心资产是组织变动事件流（时机）和你自己的关系图（路径）。这两样都不是买来的，是攒出来的——竞品能买到和你一样的人才库，买不到你的关系网，也补不回你过去半年积累的事件时间轴。

触发这个产品的那个场景

「A 司的 c 业务组并入 b 组，那这一群人都会流入市场，c 组老大可能就会看机会。」——这句话拆开，就是产品的完整工作流：顶部那条五步管道。

05Agent 怎么工作

整理和更新是 Agent 的活，不是用户的活。用户只负责说话、确认、纠错；建节点、连边、发现冲突、发现过期、发现该问什么，全部由 Agent 做。

这是生死线

一个需要用户自己填表维护的图，三周之后一定是废的。这是这类产品最常见的死法——不是功能不够，是数据饿死。所以下面每一条设计，都在回答同一个问题：怎么让用户什么都不用做，图还能保持准确。

5.1　意图的划分维度必须换一个

阿桥的登记表里 intent = 受众（居民 / 窗口 / 雇主 / 政策）。本产品只有一类受众（猎头 / 招聘方），受众维度切不出东西来。所以这里的 intent = 任务：

意图用户在干什么典型问句
graph_maintenance维护图谱
Agent 主导		「我今天跟王五聊了，他说 c 组要并进 b 组」
lead_discovery找线索、判断时机「最近有哪些组织在动？」「这条现在值不值得投时间？」
path_navigation找引荐路径「我怎么够到 C 司的技术负责人？」
outreach_ops触达与跟进「王五这条我上次聊到哪了？该跟进了吗？」
为什么必须显式说明这个改动

登记表的语义一旦从「受众」变成「任务」，后面每加一行的判断标准就不一样了。不写下来，三个月后没人知道该按什么标准加——然后登记表就会变成一个什么都往里塞的杂物箱。

每个意图仍然带自己的目标、成功判据、边界、工具白名单、校验器、预算。这套结构照搬阿桥，因为它是被验证过的那部分。

5.2　工具清单

A · 抽取与写入 —— Agent 从对话里拿事实

工具风险做什么
graph_reconcile只读传入候选新事实，返回三选一：新建 / 合并到已有 / 与已有冲突。不写库
graph_apply低把对账结果落库。带幂等键，重复调用不产生重复节点
touchpoint_add低记一次接触：时间、渠道、聊了什么、结果、下一步
event_record低记一条组织变动事件，来源与证实状态必填

Reconcile 的四个判定 · Apply 的四个答复 已实现

判定含义谁能落库
create图上没有像它的东西Agent 直接落
update完全同一条记录，没有任何值相抵触Agent 直接落
merge按具名规则像某条已有记录必须人答
conflict同一条记录，某个值不一样必须人答

四个答复：create_new（是两个人）· merge_into（是同一个）· accept_change（世界变了 → 落值并生成事件）· keep_current（那个说法不对 → 不改值，但把「有人这么说过、被驳回」写进时间轴）。

合并候选的三条具名规则 —— 每条都要两个信号

规则键触发条件
same_org_same_unit_shared_surname同公司 + 同组 + 同姓 + 一个称呼是另一个的缩写（王总 → 王，是 王五 的前缀）
same_org_same_role_shared_surname同公司 + 同职务 + 同姓 + 称呼可缩写
same_org_label_contained组织 / 单元：同公司 + 一个名字包含另一个（c业务组 / c组）
为什么「王五 vs 王六」不算候选

同姓在任何一家中国公司都能匹配三分之一的人，是弱信号。规则额外要求「一个称呼是另一个的缩写」——王五和王六互相都不是前缀，所以它们是两个人。永远不靠单一弱信号，永远说出是哪两个。

工具层已交付 2026-09-10

internal/leadgraph/tool.go —— 11 个工具，四组齐全，每个带 JSON Schema、风险等级和实现。三条保证：所有对象 additionalProperties:false 且校验在进入 Run 之前（带 匹配度 的调用在门口就被拒）；不可逆操作的审批绑定这一次调用的参数哈希（给另一条记录的审批放不了这一条过）；只读工具不需要审批（给读也加闸门会训练调用方「什么都批」）。

一处如实记录的成本：这个包自带了一份 JSON Schema 子集（约 150 行），没有复用兄弟产品的 internal/tools —— 那会把它的 consent scope、role 和意图登记表一起拖进来。这是已知的重复，也是 Q4 拆仓时第一个该抽成共享库的部分。

为什么 reconcile 和 apply 必须拆成两个工具

这是本产品最关键的一个结构决定。如果让模型一边判断一边写库，「这两个王五是不是同一个人」就成了一次不可复现的模型判断：同一份数据两次可能给出不同答案，用户的图会随机漂移，而且没法写测试。

拆开之后，合并与冲突的判定是一个确定性的、可测试的、可回归的只读函数；模型只负责两件它擅长的事——把话变成候选事实，以及把冲突讲给用户听。

5.3　Agent 的维护循环

Agent 有两条跑动路径，缺一不可。

为什么回执只有一行、问题最多一个

用户是在干别的事的过程中顺口说了那句话。一个每次都跳出来确认三件事的助手，第二天就会被绕开——用户会停止告诉它任何事，图随之饿死。「不打断」不是体验优化，是这个产品能不能活下来的前提。

路径一的三条硬约束 已实现

约束为什么
一轮最多一个问题不是每条一个，是总共一个。其余进队列，跨轮保留
没记下东西就不出回执每轮都有回执 = 噪音；噪音会让「一行回执」变成用户学会跳过的东西
安静不等于放行这轮没空问的判断一条都不落库。被动 ≠ 宽松
两个排序决定

① 冲突优先于合并。冲突意味着图上存着一条被用户刚说的话推翻的事实——不问，下一次回答就会引用一条他刚纠正过的事实，这是最快丢掉信任的方式。未解决的合并只是多一条重复记录：看得见、无害、以后能修。

② 问过一次没答的，下一轮不再问。用户没答的问题第二次并不会更紧急。重复问是唠叨，唠叨会训练用户忽略这个通道。

队列按席位，不按团队

问题是关于这个人自己那次对话的。一个没听过那场对话的同事去回答，比没人回答更糟。顾问离职时队列随他删除——留着是一份只会增长、没人能答的积压。

另外，「算了」和「我决定了」是两个 API（DropPending vs Answer），这样「我不想决定」永远不会在记录里被当成「我决定了」。

为什么必须有路径二

只靠路径一，图只会记录用户已经知道的事——而这个产品的价值恰恰是告诉用户他还不知道的事。没有路径二，它就是个手工 CRM，卖不出溢价。

5.4　冲突怎么处理

这是 Agent 做整理最难的一段，也是最容易被做成「静默覆盖」的一段。

冲突类型例子处理规则
同一实体
不同叫法		王五 / 王总 / 老王reconcile 给出合并候选 + 依据（同公司同组同职务），必须用户确认才合并。绝不自动合并
同一字段
不同值		上次说组长
这次说总监		默认解释为「发生了变化」：生成一条晋升事件，旧值保留在时间轴上；同时问一句「是升了，还是我之前记错了？」
传闻与官方
冲突		听说要裁撤
公告说是合并		官方优先成为当前值，传闻不删，留在时间轴上并标注「后被公告推翻」
同一情报
重复进来		用户说过一遍
新闻里又抓到		幂等键 =（来源标识, 实体键）。重复不产生新节点，但证实状态从 听说 升到 多源印证
两条铁律

一 · 绝不静默覆盖。任何对已有字段的修改都留痕、都可回溯。这类系统最致命的失败是——用户几周后基于一个被悄悄改过的事实做了决定，而且没有任何痕迹能让他发现。宁可多问一句，不可静默改一次。

二 · 默认解释为「世界变了」，而不是「用户记错了」。这个产品的全部价值建立在追踪变化上。把变化当成录入错误改掉，等于把产品最值钱的那类数据当垃圾删了。

关键字段

字段作用
UnitPath["A司","技术中心","c业务组"] —— 架构树的层级
Intel[]支撑这个节点的每一条情报：来源类型、URL、原文片段、抓取时间、证实状态

三个刻意的设计决定

① Intel 为空的边，store 层直接拒收。让「每条线都有来源」成为存储层的性质，而不是靠调用方自觉。校验器是第二道防线，不是第一道。

② 组织调整时旧边写 ValidUntil 而不是删除。三个月后要回答「他当时在哪个组」。删掉就答不出来了，而这正是本产品的核心资产。

③ unit 是一等公民节点，不是 person 上的一个字符串字段。组织变动的主体是组不是人。「c 组并入 b 组」必须能一次性作用到组里所有人，字符串字段做不到这件事。

07情报来源分级与合规红线

这一节决定公司会不会出事。前面所有设计都可以慢慢演进，这一节的红线必须在第一行代码之前定死。

级别来源能不能用
自有用户自己的接触、团队内共享、朋友告知能。标 user_said，默认「听说」
合法公开公司公告、财报、官方新闻、招聘网站公开 JD、工商登记变更能。必须存 URL + 抓取时间 + 原文片段
采购第三方联系方式库默认不接。要接必须先拿到供应商的来源合法性证明与授权链路说明
抓取领英 / 脉脉 / BOSS 等平台的简历、动态、通讯录禁止，写死在代码里
为什么「抓平台」这条必须写死，而不是做成开关

它同时踩三样东西，而且代价是刑事和民事级别，不是罚款级别：① 违反平台服务条款——账号封禁、平台民事索赔，国内已有多起判例；② 可能触及《刑法》285 条「非法获取计算机信息系统数据」——绕过反爬措施获取数据；③ 《个人信息保护法》——抓来的个人信息没有任何合法处理依据。

开关会被打开。所以它不是一个默认关闭的配置项，而是一份禁止来源清单 + 一道阻断级校验器 + 一条围栏测试。要打开它，需要改代码、过评审、留下记录。

P6 + P9 一起做的原因：它们共用同一份记录 已实现

P6 要知道「上次这个源说了什么」才能发现某个组不再招人；P9 要知道「这条事实从哪来」才能回答主体查询。这是同一张表：每次抓取一行，无论有没有产出。

保留「什么都没产出」的那些行才是关键

「我们看过了，没有」和「我们从来没看」是两个不同的答案，只有台账分得清。

P6 的规则为什么
禁止来源在发请求之前就被拒只在存储层拒绝已经太晚：那时爬取已经发生、对方的日志已经存在、ToS 已经违反。Source 必须声明它会访问哪些 host，声明里带禁止 host 的源一次请求都不会发出；返回结果里再查一遍 URL 是纵深防御，不是主闸门
招聘广告产出 unit，不产出 event一条广告说明这个组存在、在招人；它没有说发生了什么。硬变成事件就是制造新闻。真正的信号是时间上的缺席（HiringGap 从台账算），不是从一条广告里猜
工商变更 / 公司公告 = 官方公布这是公司自己在说话，是本包里唯一产生这个等级的地方
预警只说两件用户已经告诉过我们的事

「A 司 c 组并入 b 组（公告）+ 你图上在 c 组的有 3 个人」。没有分数、没有排序、不预测任何人的去留 —— §05.7 那条边界的落点。而且一个事件只预警一次：重复提醒等于催促行动，这个功能的定位是「别错过」，不是「快去联系」。

预警里「谁在那个组」直接复用架构树，所以它自动继承了「已截止的隶属不回落到旧组」那条规则。

7.2　敏感个人信息一律不入库 已实现

健康、婚育、宗教、政治、金融账户、行踪轨迹——字段层面拦截，不是「尽量不记」。

两个理由，一个合规一个业务

① 《个人信息保护法》第 28–29 条：敏感个人信息需要单独同意加必要性论证，本产品拿不到。
② 它对判断根本没用。加进去只增加风险，不增加成单率。

落地：健康 / 婚育 / 宗教 / 政治 / 金融证件 / 行踪 六类词表，在写入时拒绝，所有接受自由文本的路径都接了（节点、边、接触记录、私人备注）。

误伤是明说的取舍

「残疾证办理专员」是真实岗位。所以词表刻意窄而具体——多字、难以无辜使用的词，不用「病」「残疾」这种裸词。误伤时报错指名是哪个词、哪一类，让用户一次改对而不是猜。加宽这张表是产品决策，不是 bug fix。

7.3　被记录人的权利通道

被记录的人有权查询、更正、删除关于自己的记录（《个人信息保护法》44–47 条）。必须有一条真实可走完的通道：查询返回系统里关于他的全部记录及来源；更正要改并留痕；删除是真删，包括团队共享副本和导出记录里的引用。

两个需要你知道的判断

① SubjectRecords 是本包里唯一跨团队的读，而且不接受 View。一个人的权利是关于他自己的，不是关于我们的租户模型；让他先说出「可能哪几个团队存了我」是不可能的，只答一个团队就是答错。它是运营动作，每碰一个团队写一条审计。

② 私人备注会交给主体本人。这是真实的张力——顾问的私人判断变成可披露的，会改变他愿意写什么——这里按法律口径判给主体。建议找法务确认后再定稿。

为什么这不只是合规成本

这是风控。to B 客户最怕的不是罚款，是一封投诉信让客户的品牌部介入。有一条能立刻走完的删除通道，这件事停在客服层面；没有，它会一路走到客户的法务。

08线索评分：可以有分数，但分数必须能被拆开

要「离职提醒」就是要排序。这里不回避排序，但对分数有三条硬约束。

8.1　评的是「处境」，主体尽量是组织单元，不是人

线索 · c 业务组 · 稳定性信号窗口期 ≈ 3 个月
+++并入 b 组公告 · 8/29 官方
++该组 6 个月无新增招聘招聘网站 · 9/1 多源
−组长上季度公开分享过团队规划公开动态 · 6/12
图上你认识 3 个人：王五（组长）、张三、李四。2 跳可达
为什么主体是组不是人

组织级信号推不出个人意图。硬推出来的「王五 87% 会离职」是编的——猎头拿去用，第一句话就会露馅，转化率反而更低。个人级分数只在有个人级信号时才成立（本人公开表达、简历更新、公开求职），而这类信号本来就少。

8.2　分数必须附带构成它的具名信号 已实现

界面上永远是「因为这几条」，不是一个孤零零的数字。

做成结构上不可能违反，而不是事后检查

Score() 是方法，不是字段 —— 它由 Signals 求和得出。于是「持有一个没有证据的分数」这件事在类型上就不存在，也没有任何未来的代码路径能忘记附上证据。一道校验器只是它的弱化版。

猎头要用这个分数决定今天打哪通电话。一个黑箱数字既没法验证也没法反驳，用错了还没法归因。可拆开的分数才是能改进的分数。

权重是一张表，窗口期自带定义

每个数字都在界面上紧挨着它的来源；散进 if 里，恰好会让榜单在有人不同意它的时候解释不清 —— 而那正是解释存在的意义。事件权重随证实等级上升（公告 3 / 多源 2 / 听说 1）：如果公告和传闻等重，追踪证实等级就只是装饰。

界面写的是「窗口期约剩 77 天（自最近一条信号起算 90 天）」—— 90 天是约定不是测量，所以印在数字旁边。一个需要读者信任的数字，不是一个被解释过的数字。

走查又抓到两个（第二次证明「跑测试 ≠ 走查」）

① 同一个组在榜上出现两行，一行带人一行不带 —— 「c业务组」在图上有两个位置。榜单原本是「每个图节点一行」，而它应该是每个「情形」一行：事件说的是「A司的c业务组」，这样的情形只有一个。已按 (公司, 组名) 合并、人去重、信号只算一次，并在行上注明名字出现在几个位置。

② Go 代码里写了英文界面句子（"no advert seen for 240 days"）出现在全中文页面上 —— 我自己在 P3 定的规矩被自己破了。已改为信号只带 Kind + Days，句子由模板渲染。

8.3　分数不进导出、不进 API、不出现在给候选人看的任何地方

为什么这条要在两层各拦一次

一份「离职可能性排行榜」外流的后果远不止是尴尬——榜上的人可能因此在自己公司里出事。导出和 API 是两条独立的出口，各拦一次，各配一条围栏测试。

09图谱与三个视图

视图回答什么问题形态
组织架构图 已实现A 司这个组都有谁？层级树。已记录实线、只被提过虚线、不知道就空着，不补全

架构树：核心不是画树，是把「不知道」画出来 已实现

规则落点
不凭空造层级树只由有人说过的路径构成：已记录的 unit 路径 + 能放进去的人的路径。中间不插值
只被提过的层级标 mentioned界面画虚线：它有名字，但我们手上没有关于它的任何东西
放不进去的人列出来一个被悄悄丢掉的人，和一个不存在的人，在页面上长得一模一样
同名两处报歧义「c业务组」出现在两个深度：可能是同一个组，也可能是两个，都说出来而不是挑一个
计数来自树本身从别处算的汇总，就是「9 个人的列表上面写着 12 人」的来源
已截止的隶属，不回落到人身上那条路径

组织调整后 belongs_to 被截止，但这个人自己的 UnitPath 字段还写着老组。如果「找不到有效隶属就去读那个字段」，就会把他放回他刚离开的组 —— 而那正是有人要照着这张图去联系他的时刻，是这张图能犯的最贵的错。

规则：只要他有过隶属关系，就只认还有效的那些；全截止了就是「不知道他现在在哪」，并附上截止日期。围栏同时验证「调整后不在旧组」和「调整前的历史仍然答得出来」。

文字兜底是从架构树推导的，不是另查一遍

它们回答同一个问题，各写一份两次改动之内就会不一致。而它是图谱在低带宽 / 渲染失败时的兜底 —— 一个和它所替代的东西说法不一致的兜底，比没有兜底更糟。它保留了「已记录 / 只被提过」的区分：兜底不能显得比原件更确定。

为什么引荐路径比「离职预测」更值钱

① 它建立在你自己的关系记录上，没有任何第三方数据风险；
② 它直接决定回复率——「张三让我联系你」和陌生开发信是两个数量级；
③ 别人抄不走。竞品能买到同样的人才库，买不到你的关系网。

Strength 只能由用户填，系统不推断。系统推不出「你跟这个人有多熟」——硬推的结果是把一条弱关系当强关系用出去，尴尬的是用户本人。

路径从哪里起算：这个问题只有一个诚实答案 已实现

图里没有「我」这个节点——图存的是外部的人，不是团队自己。所以「我能去问谁」必须从用户亲口说过的东西里推导，而这个模型里只有一样：关系强度。于是 Strength 从装饰变成承重结构：标过强度 = 我认识他 = 可以作为路径起点。

空结果含义下一步
NoSeeds你还没标过任何人的关系强度告诉我你认识谁
路径为空你认识的人里没有一条连得上他换个人问 / 扩大跳数

这两种在屏幕上长得一模一样，但补救方式完全不同，所以必须分开。

最弱一环优先于跳数少

一条链条的强度取决于最弱那一环。通过一个不太熟的人的 1 跳，比通过两个熟人的 2 跳更差。先给短的那条，就是让用户挑一条走不通的路。围栏专门构造了这个对照：把「1 跳弱」和「2 跳强」摆在一起，断言强的那条排前面。

另外 只走关系线，不走架构线：汇报线和隶属线是结构，不是「这个人会帮我引荐」。把汇报线当温路径，正好产出那种让托人的人尴尬的引荐。

Q1 的一个直接后果

别人跟别人有多熟，你看不到——强度是席位私有的。所以路径里不属于你的那一跳标 Mine=false / Strength=0，界面要说「这一跳不是你自己的关系」，而不是显示一个看起来很确定的 0。

接触记录：为什么是团队的 已实现

它挡住的那一个失误

「上周有人已经打过他电话了」是唯一能阻止两个顾问一周内先后 cold-call 同一个人的事实——而那正是让公司在它最想打动的人面前显得没组织的失误。它必须在打电话那个顾问离职之后仍然存在。

所以：记录归团队，只有上面那条私人印象归席位。字段上也照这条切——Topic / Outcome / NextStep 是事实（说了什么），归团队；「他听起来很敷衍」是判断，进 Note（私有）。

一个刻意的例外：接触记录不要求来源。其他记录都必须说明出处，因为它们是关于第三方、会被拿去行动的断言。接触记录本身就是它自己的出处：谁、什么时候、哪轮对话。没有外部出处可引，因为出处就是填它的人。

图谱是叠加层，文字才是页面 已实现

服务端把文字版清单直接渲染进 HTML，图谱是脚本在它上面叠的一层。

为什么不能反过来

一个需要先取数、再渲染才能出现的「兜底」根本不是兜底 —— 它恰好在它该起作用的那些条件下失效。没有脚本、链路慢、渲染出错、打印页面，读者拿到的仍是每个人、每个组、每个「待确认」角标。围栏把 HTML 在第一个 <script> 之前截断，断言这些内容已经在里面了。

视觉编码含义
颜色节点类别
虚线圈只被提过、没有记录的组
虚线未证实的关系
大小恒定 —— 什么都不编码

围栏直接读发布出去的 graph.js，断言半径只来自常量、线宽不来自任何 strength/score；另一条断言 payload 里根本没有 score/rank/weight/size 这些键 —— 数据里没有，未来任何一版样式表都没法开始编码它。

布局先算完再画

力导向若只在 requestAnimationFrame 里收敛，它就只在标签页可见时收敛：渲染进隐藏标签、打印、截图或被节流的后台，它画完第一帧混乱状态就停 —— 而那一帧看起来像一张画完的图。所以模拟在第一次绘制之前同步跑完，拖拽时局部重算，没有任何自走的动画。

界面走查抓到两个真 bug —— 这就是验收标准里写「走查」的原因

① 预警说「你图上这个组还没有人」，而那个组里有 3 个人。事件只知道公司 + 组，而用户把那个组放在了更深的位置（A司 › 技术中心 › c业务组）。按整条路径匹配，恰好在用户告诉了我们更多结构的时候找不到人 —— 方向反了。

② 图上根本没有架构线，只有关系线。一个没被记录过的层级在图上完全不存在，于是「架构图 + 关系线」只做了一半 —— 更糟的是，图看起来比它本该更丰富的那个文字清单还要整洁。已补：层级和人-组归属都进图，只被提过的层级作为虚线框节点，且这些线标记为 Derived，绝不和「有人记录过的隶属」混为一谈。

一个设计观察，不是 bug

真实数据里几乎所有线都是「未证实」（大多数事实来自一次对话、单一来源），所以虚线会变成默认样式、失去区分度。当前是诚实的，但视觉信息量低。P7 之后可以考虑把「已证实」做成更明显的正向标记，而不是靠「没有虚线」来表达。

降级：图谱是展示层，它不产生任何新信息。

10批量导入：格式要求

核心原则：适配你的表，不要求你改表。一个要求用户先把列名改成模板的导入，等于「先做数据清洗再用产品」—— 没人会做。

为什么导入是最该先做的一件事

每一个派生功能都需要用户还没给我们的数据：path_find 在有人标过关系强度之前返回 NoSeeds；HiringGap 在台账攒够几个月历史之前返回 nil；一条预警既要事件、又要你在那个组里已经认识的人。空图上这个产品什么都不知道、什么都说不出来 —— 而顾问手上早就有一份表格。

只有一条硬要求

第一行必须是表头。除此之外，读不懂的文件不拒收，而是暂存下来让人看。

「整个文件拒收」就是把「先做数据清洗」挪到了失败之后

一个读不懂的文件应该是一次对话，不是一次拒绝：系统暂存它，连同表头和前 5 行样例，让 agent 看着提议「第 1 列看起来是姓名（前三行是王五 / 张三 / 李四），对吗？」，用户确认之后整份文件重读一遍。

出问题时 agent 怎么修 已实现

import_remap 一个工具，四种修法 —— 全部是「用户确认之后由 agent 转达」，不是 agent 自己猜。

修法场景例子
改列映射别名表不认识用户的叫法客户名称 → 姓名；表头空白时可以按位置 #1
翻译取值文件用的是用户自己的词汇很熟→3、一般→2。这不是缺陷，是他就这么写的
补单元格某行缺了姓名用户说「第 4 行是李四」→ agent 转达。agent 不许自己编
排除行用户说这几行不要第 3 行忽略
修改是「整份重读」，不是「打补丁」

每一次修改都从原始字节重新读一遍全文件 —— 所以不存在「修了一半的计划」，用户看到的永远是一份完整连贯的读法，改三次也不会攒出一个谁也说不清的状态。围栏验证：再发一次空的修改，文件会回到最初的状态。

修改仍然过所有闸门：敏感值补不进来；指向一个不存在的列名会被忽略而不是悄悄读成第 0 列；只有上传的那个席位能改。

为什么 import_remap 是「写」不是「只读」：它改的是暂存的读法，不写图。所以它不需要审批 —— 审批在后面的 import_commit 上，覆盖的是它产出的那份读法。

疑似已有的同一个人不静默新建，变成一条「需要你决定」，走和对话路径完全一样的合并机制

同一份表里 200 行都说同一件事，证实等级仍然是「听说」。否则一份表格就能把自己抬成「多源印证」。

Agent 在导入里做什么、不做什么 已实现

它产不出文件 —— 上传是用户的动作。所以形状是：用户上传 → 系统出计划 → agent 讲解并陪着走 → 用户拍板 → 落库。

Agent 能做工具风险
把计划讲成人话import_summary只读
追问「这些人里你最熟的是哪几个」rating_gap只读
记下用户说的熟悉程度rate_contact写
落库import_commit不可逆 · 需审批
为什么落库是「不可逆」级

转达一条合并决定是聊天；一次性转达两百行的决定是另一回事。它拿和删除同级的闸门 —— 审批绑定的是这一次调用的全部参数，包括里面每一条决定。所以「同意导入这份表」不等于「同意把第 3 行并进王五」。

导入的待办不进对话队列

两个不同的时刻，两套结构

RecordTurn 一轮最多一个问题，是因为用户在干别的事。而导入是用户正盯着屏幕的时刻 —— 12 条决定应该在一个 review 屏上一次过。共用一条队列会两头不讨好：对话被 12 个它本来设计成永远不会问的问题淹掉，或者导入要聊 12 轮。

暂存的计划只在内存里，没有新建表。一次 review 就几分钟；为了「进程重启」建表 + 迁移 + 生命周期，换来的补救是「重新传一次文件」。等 review 变成长流程再持久化，现在不。

‼️ 导入之后必须有人问那一句

导入 200 个人、一条熟悉程度都没标 → 图是满的，path_find 仍然返回 NoSeeds。这个包里没有任何别的东西会去问，所以 RatingGap 就是干这个的：报出已标 / 未标，外加最多 10 个名字（10 个是人会回答的清单，200 个是人会关掉的清单）。

名字按姓名排序，不按任何别的东西排。那个看起来很贴心的排法——「谁连着的边最多、谁能打开最多路径」——就是换了顶帽子的给人排名，而且用户比图更清楚自己跟谁熟。

‼️ 已知缺口：联系方式没有进来，需要拍板

猎头的表里最主要的东西是手机号和邮箱，但 Node 目前没有联系方式字段，我没有偷偷加。理由：加字段是扩接口表面积，而且「存不存、加不加密、导出时怎么处理」是一组独立的产品 + 安全决策，不该顺手塞进导入里。

当前行为：这些列会出现在「未识别列」里被报出来 —— 你看得到它们被忽略了，但没有被存下来。要不要存，请拍板。

11测试围栏

每一条围栏对应上面一条设计决定。围栏变红时，要能立刻找到当初为什么这样写。

绿的测试证明不了围栏存在

标 已过 的每一条都做过变异演练：把对应的守卫从产品代码里删掉，确认这条用例真的会变红，然后还原。一条删掉守卫仍然全绿的测试，比没有测试更糟 —— 它会让人以为这里有保护。

P5 就抓到两道真空的。一道是我的尺子错了（变异打在了一个冗余的判断上，真正的机制在另一行）；另一道是代码里真有一个永远不改变结果的分支——删掉它测试全绿。它读起来像保护，实际什么也没保护，已经合并成一条规则一行代码。
